# 中文口语录音转写与讲评

把一段中文口语录音变成**可信的逐字稿**，再基于**实测数据**给出讲评。

## 一键用法

```bash
# 转写（默认 medium；建议先用 small 快速看内容）
bash {baseDir}/scripts/run.sh transcribe "<音频路径>" [small|medium] [输出目录]

# 实测指标（语速、停顿、响度、口语词频）
bash {baseDir}/scripts/run.sh metrics "<音频路径>" [逐字稿json]
```

`run.sh` 已处理三件事：Python 自动探测、Windows 原生程序的路径转换（cygpath）、HuggingFace 镜像环境变量。

## 环境（一次性）

- **ffmpeg / ffprobe** — 系统需自带，`metrics.py` 强依赖
- **faster-whisper** — 装在托管 venv 里即可：`pip install faster-whisper`（首次跑模型会自动下载）
- **Python 探测顺序**：环境变量 `WORKBUDDY_PYTHON` > `~/.workbuddy` 托管 venv（Win/Mac 两种路径）> PATH 里的 `python`
- 模型下载走 `HF_ENDPOINT=https://hf-mirror.com HF_HUB_DISABLE_XET=1`（脚本内已设）。
  **坑**：国内网络直连 HuggingFace 的 xet 通道会 401，必须关 xet + 换镜像

### 若 Bash 工具报 `dirname: command not found`

部分环境下 Bash 启动时 PATH 被 shim 破坏，`ls`/`dirname` 全部失效。**任何命令前先显式修复 PATH**（按本机实际版本号调整）：

```bash
export PATH="/usr/bin:/bin:$HOME/.workbuddy/binaries/python/versions/<版本>:$HOME/.workbuddy/binaries/node/versions/<版本>:$PATH"
```

且 `cd` 要写绝对路径、与后续命令用 `&&` 串联（shim 会把 `cd` 的目录参数丢掉）。

> Windows 上**不要用 PowerShell 工具取数据**，stdout 捕获可能为空；一律走 Bash。

## 模型选择与耗时（CPU int8 实测）

| 模型 | 磁盘 | 下载 | 5 分钟音频转写 | 中文口语质量 |
|---|---|---|---|---|
| small | ~460MB | 快 | 约 50 秒 | 错字多，只能抓大意 |
| medium | 1.53GB | 约 45 分钟（0.55MB/s） | 约 10 分钟 | 明显可用，专有名词仍需核对 |

**策略：先用 small 跑一遍看内容，同时后台下 medium，再用 medium 出正式稿。** 下载 + 转写放同一个后台任务里，跑完会自动通知。

## 核心方法一：多提示词交叉核对（校正听辨错误）

`initial_prompt` 会**强引导**模型的输出，所以不能只靠它。正确做法是**三角验证**：

1. 对同一片段跑**多次**，每次换不同的 `initial_prompt`
2. **无提示词（`None`）时仍自发出现**的结果 → 高置信，采信
3. **只在被提示时才出现**的结果 → 低置信，是提示词的复读，不能采信
4. 无提示词时输出**乱码/不一致** → 标 `【?】` 让用户确认，不要编

实例：

| 现象 | 判断 |
|---|---|
| 结尾句无提示词时自发输出"脱贫攻坚任务" | ✅ 采信 |
| "三十二个同学"只在被提示时才出现 | ❌ 不可信，标 `【?】` |
| 台风名被识别成乱码"8V" | 🔍 转外部核查 → 当年第 9 号台风"巴威" |

## 核心方法二：外部事实核查救回专有名词

ASR 对**专有名词**（台风名、地名、机构名、专业术语）必然出错，且往往输出乱码。
**听到乱码 = 有个专有名词。** 用 `WebSearch` 按「时间 + 地点」反查，常能一击命中。

## 核心方法三：音频实测指标

录音本身是客观证据，比"感觉讲得快"有力得多：

- **语速**：中文演讲舒适区 **180–220 字/分钟**，超过就是"赶"
- **停顿**：`silencedetect` 阈值 −32dB、时长 >0.35s；段落之间应有 **1.5–2 秒**留白
- **响度**：EBU R128，`-19 ~ -16 LUFS` 正常；低于 −20 偏低，句尾易丢音
- **LRA**：>9 LU 说明音量起伏大
- **段落占比**：把逐字稿按时间轴切段算占比——汇报类场合**成果占比应 >50%**，困难/过程占比过高是典型结构病
- **口语词频**：数"然后/这个/就是/其实/比较"的出现次数

## 坑（都踩过）

1. **ffmpeg 切片必须用输出侧 seek**：`-i in.m4a -ss N -t M`。用输入侧 `-ss`（写在 `-i` 前）会**窗口偏移**，切出来的内容和预期不符。
2. **`-to` 与输入侧 `-ss` 混用语义有歧义**，一律改用 `-t <时长>`。
3. 切片预处理有帮助：`-af "highpass=f=90,afftdn=nr=10"`。
4. **`initial_prompt` 不要超过两三句**，长提示词会被当成待转写内容**泄漏进输出**（实测出现过提示词被原文输出）。
5. 短片段上模型会**复读循环**（同一句重复几十遍），说明该处音频低置信或有大段静音，别当成真值。
6. **不要用 PowerShell 工具取数据**，stdout 捕获为空。
7. 转写在 CPU 上很吃时间，长任务放后台，别在前台等超时。

## 讲评的输出框架

讲评要有判断、有依据、有优先级，不要罗列优点缺点：

1. **按场景定基准**——"经历分享"和"成果汇报/答辩"的标准完全不同，先说清按哪个评
2. **一句话结论**——分场景各给一个判断
3. **实测数据表**——每项给「实测 / 参考区间 / 判断」
4. **立得住的地方**（2–3 条，说清为什么立得住）
5. **结构问题按严重程度排序**，不按出现顺序
6. **最有价值的一句被浪费在哪**——几乎每段演讲都有，指出来
7. **改造后的骨架**（表格：原结构/原时长/建议结构/建议时长）
8. **可直接替换的原句**（Before / After，缺事实的地方用 `【】` 占位并标注需用户补）
9. **需用户确认的听不清处**——列成表，给疑似真值

## 边界

- 只转写口播，画面文字（PPT/字幕贴图）不包含
- 会议/多人场景需先做说话人分离（本 skill 未覆盖），否则会把多人内容混成一稿
- 采样模型对口语够用，**关键句必须人工确认**，不要直接引用未核对的输出
