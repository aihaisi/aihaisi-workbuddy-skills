# 游戏 AI 最优性验证

## 何时用

- 用户拿着一个组合博弈题目要做玩法原型，要求 "AI 按最佳策略行动"
- 怀疑现有 AI 判据写错了（表现：AI 在明显占优的局面乱走）
- 需要给"这个 AI 是最优的"下结论，而不是"看着挺聪明"

**不适用**：有隐藏信息 / 随机事件 / 实时动作的游戏（搜索树爆炸，改用启发式 + 胜率评估）。

## 核心原则：别急着写 AI，先证结构性质

**绝大多数取物类博弈都有"只剩一个变量"的化简。** 找到它，AI 就从"搜索"退化成"查表"，最优性也变得可证。

验证顺序（缺一层就会误判）：

| 层 | 做什么 | 证明什么 |
|---|---|---|
| ① 结构性质 | 博弈树归纳，找必败态的形态约束 | 必败态长什么样（往往能推出"走法唯一"） |
| ② 闭式解 | O(n) 递推算胜负 + 走法 | 可实现的策略 |
| ③ 逐状态交叉验证 | 暴力 DP vs 闭式解，穷举所有可达状态 | 闭式解没写错 |
| ④ 自对弈端到端 | 双方都走最优，终局胜者 == 开局裁决 | 走法选择（不只是胜负判断）是对的 |
| ⑤ 新旧对战 | 旧 AI vs 新 AI 胜率 | 量化"修好了"而不是"感觉修好了" |
| ⑥ 官方样例对拍 | 题面自带样例 vs 求解器输出 | **外部权威**校准（见下） |

**⑥ 是最容易被漏掉、也是唯一真正独立的一层。** ①②③ 都只是在跟"自己的暴力解"对账，
两者可能同时错（对规则的理解本身就偏了）。原型的题目若出自公开题库（洛谷 / Codeforces / 牛客…），
题面通常自带样例与期望输出 —— 把它连同期望值**硬编码进验证脚本**，一次对拍就能锁住整条判据：

```js
const LUOGU_SAMPLES = [                       // 来源：洛谷 U145698 题面样例
  { a: [1, 1, 1],    expect: 'Elaina' },
  { a: [1, 2, 1],    expect: 'Fran'   },
  { a: [3, 4, 5],    expect: 'Elaina' },     // 注意样例要连"期望赢家"一起抄，
  { a: [1, 2, 1, 2], expect: 'Fran'   },     // 只抄输入等于没对拍
  { a: [8, 1],       expect: 'Elaina' },
];
const got = analyzePosition(a).canWin ? 'Elaina' : 'Fran';
```

顺手把题面的**数据范围**也抄进自对弈的随机参数（如 `1 ≤ n ≤ 50, 1 ≤ a_i ≤ 1e6`），
这样"穷举验证的小值域"和"自对弈的大值域"刚好覆盖题面的完整边界。

### ① 的实战价值：本案例推出了一条省掉整段代码的定理

顺序取蘑菇（n 个盘子串行解锁，每次从最左未空盘取 1~k 个，取最后一个的赢）：

> **当前盘剩余 m ≥ 2 ⇒ 轮到的人必胜。** 因为他要么一次取空把"开局必败的下一盘"丢给对手，要么只留 1 个把对手顶住，二者必居其一。

**推论：必败态必然是 m == 1，而 m == 1 时走法唯一。** 所以——

> 最优 AI **不存在** "必败时怎么挣扎"的自由度。任何 `if (必败态) 随机取` 的分支都是错的，
> 随机只会把本来赢的局输掉。**"必败时随机捣乱等玩家失误"是伪需求。**

（想让它"给玩家机会"是**难度设计**问题，应该显式引入按概率的次优走法，而不是藏在必败分支里。）

## 实现：求解器单独成块，供验证脚本抽取

把求解器包在标记块里，**验证脚本从交付文件抽出这段代码执行**，而不是另抄一份：

```js
/* ==== MUSHROOM-SOLVER BEGIN ==== */
function computeLosingFlags(plates) {     // lose[j] = 轮到你从第 j 盘开始处理时必输吗
  const n = plates.length;
  const lose = new Array(n + 1);
  lose[n] = true;                         // 盘面已空 → 无子可取者判负
  for (let j = n - 1; j >= 0; j--) lose[j] = (plates[j] === 1) ? !lose[j + 1] : false;
  return lose;
}
function analyzePosition(plates, activeIndex, remaining) { /* 返回 {canWin, move} */ }
/* ==== MUSHROOM-SOLVER END ==== */
```

```js
const html = readFileSync('index.html', 'utf8');
const blk = html.match(/\/\* ==== MUSHROOM-SOLVER BEGIN ==== \*\/([\s\S]*?)\/\* ==== MUSHROOM-SOLVER END ==== \*\//)[1];
const { computeLosingFlags, analyzePosition } = new Function(blk + ';return {computeLosingFlags, analyzePosition};')();
```

**抽取而非复制，是这套流程最关键的一步**——否则你测的是副本，上线的是另一版，"测试全绿但线上还是错"。

## 暴力参照：博弈树 DP

```js
function bruteWin(a) {                     // 返回 win(当前盘下标, 该盘剩余)
  const memo = new Map();
  function win(i, m) {
    if (i >= a.length) return false;       // 无子可取 → 判负
    const key = i * 1e7 + m;
    if (memo.has(key)) return memo.get(key);
    let res = false;
    for (let take = 1; take <= m && !res; take++) {
      const next = take === m ? win(i + 1, i + 1 < a.length ? a[i + 1] : 0) : win(i, m - take);
      if (!next) res = true;
    }
    memo.set(key, res);
    return res;
  }
  return win;
}
```

状态数爆炸前先算清楚：n ≤ 5、a_i ≤ 4 就有 1364 个盘面 / 约 1.6 万个可达状态，够用。

## 必写的四类断言

```js
// 1) 胜负判断逐状态一致
if (info.canWin !== bruteWin(i, m)) fail(`胜负判断错误 [${a}] i=${i} m=${m}`);

// 2) 走法最优性：这一步必须把对手送进必败态（比"胜负对"更强的断言）
const oppLoses = info.move === m
  ? (i + 1 >= a.length ? false : win(i + 1, a[i + 1]))
  : win(i, m - info.move);
if (oppLoses !== false) fail('走法非最优：留给对手的是必胜态');

// 3) 必败态走法唯一性（守住"不存在抉择空间"这条定理）
if (!info.canWin && m !== 1) fail(`必败态但 m=${m} > 1，出现意料之外的抉择空间`);

// 4) 大值域自对弈：双方都走最优，胜者必须 == 开局裁决
//    n=50、a_i=1e6 的随机盘面跑 2000 局（暴力 DP 跑不动，只能靠自对弈兜底）
```

断言 ② 是重点：**只验"谁赢"会漏掉"能赢但走错"**。AI 最优性必须验到走法层面。

## 本案例的数字（可作为量级参考）

| 指标 | 旧 AI | 新 AI |
|---|---|---|
| 逐状态判对率（15930 个可达状态） | 50.8% | 100% |
| 进入"随机捣乱"分支时**实际是必胜态**的比例 | 73.5% | — |
| 先手对局胜率（vs 旧 AI） | 6.4% | 96.6% |

旧判据错在哪：用**绝对下标奇偶**（`firstGT1 % 2`）判胜负，而正确判据是**相对于盘尾的距离**。绝对下标一路错，且 m 不参与判断——但 m ≥ 2 必胜是第一条定理，判据里不出现 m 本身就已经暴露了问题。

**排查信号：如果 AI 的判据里不出现"当前堆还剩几个"，它几乎一定错了。**

## 第三层：UI 门控也要单独测（穷举测不到）

求解器最优 ≠ 玩法正确。规则门控（"什么条件下允许点什么"）是**状态机**，不在求解器的状态空间里，
必须把整段 `<script>` 用 DOM 桩跑起来才验得了：

```js
const pageSrc = html.match(/<script>([\s\S]*?)<\/script>/)[1];
globalThis.document = { getElementById: (id) => cache(id) || (cache[id] = mkEl()), createElement: (t) => mkEl(t) };
globalThis.setTimeout = () => 0;               // 关掉 AI 自动回手，测试自己驱动
new Function(`${pageSrc}
globalThis.__api = { initGame, playerMove, playerSurrender, aiTurn, renderBoard,
  setPlates: (a) => { plates = a; },           // 覆盖随机出盘，换确定性盘面
  btn: () => document.getElementById('btn-surrender'),
  moves: () => moveCount };`)();
```

三个坑：

- `let` 在 `new Function` 体里是函数作用域，**必须靠末尾追加一行显式导出**（`vm` 同理）
- DOM 桩要**按 id 缓存同一个对象**，否则 `renderBoard()` 改的和你断言的不是同一个元素
- `setTimeout` 设 no-op 后 AI 不会自动回手，用 `aiTurn()` 手动驱动 → 完全确定性

### 顺序依赖的守卫函数：一行就能让分支变成死代码

```js
function isLosing() { if (isGameOver) return false; return !analyze().canWin; }
function surrender() { isGameOver = true; if (isLosing()) judgeWin(); else judgeLose(); }  // 判胜永远不可达
```

**判据：凡是"先置状态、再查询"的调用序列，都要断言两个分支都可达。** 修法双管齐下——查询函数保持纯粹
（不留外部状态守卫）**且**把查询提到置位之前，既修好又防复发。

配套断言：分别喂一个"该判胜"和一个"该判负"的输入，断言两种结算都出现过。**只测一种等于没测。**

## 变异测试：证明你的断言真的会失败

**能通过的断言不代表有效，能失败才算。** 对每种真实缺陷造一个变异体，跑一遍验证器，必须被抓到：

```js
const mutants = [
  ['判胜/判负对调',            (h) => h.replace(/a \? 'W' : 'L'/, "a ? 'L' : 'W'")],
  ['门控放宽 === 0 → < 2',    (h) => h.replace(/moveCount === 0;/, 'moveCount < 2;')],
  ['判据退回绝对下标奇偶',      (h) => h.replace(/return !info\.canWin;/, 'return i % 2 === 0;')],
];
```

**逃逸的变异有两种，必须分开对待：**

| 类型 | 判据 | 处理 |
|---|---|---|
| **等价变异**（行为保持） | 能论证二者在所有可达输入下等价 | 正常，无需补断言 —— 但要把**论证**写下来 |
| **真缺口** | 找得出一个输入序列能区分二者 | 立刻补断言 |

本案例 6 个变异抓到 4 个，2 个逃逸经论证均属等价：`moveCount < 2` 因为"玩家只在偶数步行动"
而等价于 `=== 0`；`isGameOver` 守卫因为唯一调用点已把查询提到置位之前而永不触发。
**另外把"完整复原历史 bug 的组合变异"单独跑一次**（守卫 + 错误置位顺序），它必须被抓到 —— 这才是硬证据。

⚠️ **等价变异不仅要"把论证写下来"，更要让论证本身可执行。**
口头说"这俩应该等价"是自欺的高发区 —— 换成**跑一段独立脚本量化两者的差异**，
差值为 0 或落在浮点噪声内才算等价：

```js
// 变异 A：权重整体等比缩放（如 0.7/1.6 → 0.35/0.8）—— 直觉上"改了配置"，实际等价
// 论证：归一化后累积概率完全相同。用独立脚本量出来，而不是嘴上说：
let maxd = 0;
for (let i = 0; i < ca.length; i++) maxd = Math.max(maxd, Math.abs(ca[i].c - cb[i].c));
console.log('最大累积概率差 =', maxd);        // 实测 0 ⟹ 等价成立

// 变异 B：越界回落分支改成常量 —— 直觉上"改坏了"，实际不可达
// 论证：累积概率上限 = 1.0000000000000002 ≥ 1，而 rand < 1 恒成立 ⟹ 回落分支永不进入
```

**这两类恰好相反**：A 是"配置变了但行为没变"，B 是"代码变了但那一行死着"。
两者的共同点是 —— **光看代码或光看断言结果都判不出来，必须量化**。
**等价变异必须存活**：如果它们被抓，说明断言在钉**实现细节**而不是**契约**，
这种断言会在下次正常重构时误伤（把权重都减半的清理动作会被判成缺陷）。

⚠️ 沙箱里 `child_process.execFileSync` 起不来子进程（`e.status === null`、stdout 为空），
**别把这种空输出当成测试结论**。做法：用 node 只**生成**变异体目录，再用 bash 循环
逐个 `node <dir>/verify-ai.mjs` 收退出码与 `✗` 行。

⚠️ **变异生成器/运行脚本这类"要被执行的文件"必须放在项目内（如 `.mutbak/`），不能放 `/tmp`。**
某些环境下 `/tmp` 在**写入侧工具**与 **Bash 侧**不是同一目录 —— 写入文件明明"成功"，
Bash 却报 `No such file or directory`。放在项目内可绕开这个歧义（用完删掉）。

⚠️ **Windows 下源文件常是 CRLF，`replace` 的锚点用 `\n` 会命中不了"行尾含注释"的行。**
`{ n: 6, weight: 1.6 },         // 注释\n` 这样的锚点在 CRLF 文件里是 `...注释\r\n`。
改用正则 `[^\n]*\r?\n`，或先确认字节（`sed -n 'Np' f | cat -A`）再写锚点。
锚点没命中时**必须让生成器报错退出**，否则"变异其实没生成"会被误读成"变异存活"。

⚠️ **项目若有"发布副本"（`site/index.html`）或其它一致性守卫，变异体必须连副本一起改。**
否则第一个失败的是副本一致性断言，你就分不清"是本次要验的那层抓到的"还是"被无关守卫挡下的"。
生成器里对源文件的每个变异结果同时写进 `<dir>/index.html` 和 `<dir>/site/index.html`。

出盘分布侧的变异清单（本案例两轮共 13 个，**13/13 全被抓**）——
这类缺陷只差几个百分点，肉眼 review 基本发现不了，只能靠断言：

| 变异 | 意图 |
|---|---|
| 概率退回上一版 / 抬过头 / 设成 0 | 数值被误改、或被"顺手清理" |
| **反解公式漏掉 `(1−p)` 归一化** | 最隐蔽的一个：35% 只偏到 25.93% |
| 其余档被压歪（不再等概率） | 提了一档却把别的档带歪 |
| 抽样器忽略权重倍率 | 配置改了但没接上线 |
| 档位上界写错 / 盘子数上界改小 | 值域被悄悄改窄 |

**带权分布（多档不同概率）的变异清单**（本案例第三轮 7 个，**7/7 全抓**）：

| 变异 | 意图 |
|---|---|
| **删掉某个档**（n=3 被移除） | 值域被悄悄收窄 —— 断言须钉死**全部档位**的字面量，不能只钉上下界 |
| **把某档放大成主力**（权重 0.7 → 9.0） | 极端值反转（变体变成主流），需单独断言"该档占比 ∈ [10%,16%]" |
| 上限退回 / 上限悄悄提高 | 值域被改；提高的那侧同样要拦（新增档位更容易漏） |
| 权重表全改均匀 | "带权"这个设计意图被抹平 |
| 抽样器比较符反向（`<` → `>`） | 累积查表逻辑写反 —— **单调性断言**专抓这个 |
| 越界回落分支改常量 | 见上文"等价变异 B"（不可达 ⟹ 应存活） |

注意最后两行：一个该抓、一个该放。**`<` 反向**会让分布完全错乱（该抓），
而**回落分支**死着（该放）。**同一次测试里必须同时包含"该抓"和"该放"两类**，
否则你不知道自己的断言是精准还是过拟合。

## 断言自身的四种失效模式（变异测试才挖得出来）

前三种"永远通过"，第四种相反"无行为变更也失败"—— 两个极端都要校准。

写断言比写代码更容易自欺。以下三种缺陷形式上都在"验证"，实际永远通过：

| 缺陷 | 长什么样 | 后果 | 正确做法 |
|---|---|---|---|
| **恒真式断言** | 断言"配置与自身常量自洽"，如 `ns.length === PLATE_SPAN`；或拿配置常量去断言配置常量（`pOf(1) === spawn.ONE_MUSHROOM_CHANCE`） | 把上界从 3 改成 2 也照样通过；改概率时断言跟着一起变 | 钉**字面量**契约 `[3,4,5]` / `0.35`，并在消息里说明"有意修改时请同步文档" —— **这份摩擦是刻意的** |
| **硬编码 ✓ 的报告行** | `console.log('结果: ✓ 与求解器完全一致')` | 断言失败了报告仍显示 ✓ —— **比没有报告更糟** | 报告行必须由真实结果驱动（存一个 `ok` 布尔，据它渲染 ✓/✗） |
| **统计抽样的概率断言** | 抽 10 万次随机数估 `P(a=1) ≈ 35%`，容差取 ±2% | 方差导致偶发变红；为了不抖动只能放宽容差 → 又失去灵敏度 | 把抽样器写成**纯函数** `pick(rand)`，验证器在 `[0,1)` 上**穷举网格**，把分布精确算出来（误差 ≤ 档位数/网格数） |

第三条的连锁好处：抽样器一旦是纯函数，产物侧也能精确算设计指标（穷举全部盘面按概率加权），
不必再用几千局模拟去估 —— 报告里给的数字从"抽样估计"升级成"精确值"，而这两者会差出小数点后一位（85.4% vs 85.83%）。

**第四种（与第一条相反，容易在两个极端之间摇摆）：过拟合断言 —— 钉死了实现细节，而不是契约。**

| 症状 | 后果 | 正确做法 |
|---|---|---|
| 断言写成"配置里的权重数组**恰好**是 `[0.7, 1.6, 1.6, 1.6]`" | 一个**无行为影响**的清理动作（把权重整体减半）会让测试变红 —— **误伤** | 断言**可观察行为**：归一化后的**概率**落在 `[10%,16%]`、值域等于 `[3,4,5,6]` |

**判据**：拿"已知等价的变异"去测 —— 等价变异**必须存活**（见上文"等价变异"小节）。
存活 ⟹ 断言守住的是契约；被抓 ⟹ 断言在钉实现细节，下次重构就会误伤。

这条和"恒真式断言"是一对：**恒真式太松（永远绿），过拟合太紧（无行为变更也红）。**
两侧都要用变异测试校准 —— 所以变异清单里**同时要有"该抓的"和"该放的"**。

## 把 DP 展开成"人能用的规则"，当作交付物之一

闭式递推能跑通就够用了，但**把它展开成一条人类可读的规则**往往能直接解释"这个玩法的转机在哪"，
价值大于再写十行注释。本案例：

```js
// lose[j] = (a[j] === 1) ? !lose[j+1] : false   展开后 ⇒
// 数"紧随其后的连续 1 蘑菇盘"长度 r：
//   a[j] >= 2                                → 必胜
//   a[j] === 1 且 1 链被 >=2 的盘截断        → 必败 ⟺ r 为奇数
//   a[j] === 1 且 1 链延伸到盘尾             → 必败 ⟺ r 为偶数（基准被"盘空判负"翻转）
```

⚠️ **展开时最容易漏掉"链延伸到边界"这一支**：本案例第一版就漏了，随机 20 万盘面立刻报错。
所以规则写完后必须**穷举小空间全量盘面**交叉验证（`n ≤ 6, a_i ∈ [1,6]` 共 55986 个），
而不是抽几个例子看着对就收。

## 出盘分布是最好用的难度旋钮（比"AI 偶尔走次优"更干净）

想让玩法更难/更有戏剧性，**改出盘分布**通常优于让 AI 故意犯错——后者会破坏"AI 按最优行动"这个可证明的性质。

**旋钮要暴露成「目标概率」，不要暴露成「权重倍率」。** 调参时脑子里想的是概率（"提到 35%"），
反解倍率是额外的心算，而且很容易算错：设目标档权重 `b`、其余 `k` 档各 1，则

```
b / (b + k) = p        ⇒        b = k · p / (1 − p)
```

```js
const ONE_MUSHROOM_CHANCE = 0.35;                                      // 想的是概率，写的就是概率
const ONE_MUSHROOM_BOOST  = chanceToWeight(ONE_MUSHROOM_CHANCE, 1, 6);  // 自动反解 = 35/13 ≈ 2.6923
function chanceToWeight(chance, minCount, maxCount) {
    const otherBuckets = maxCount - minCount;
    const p = Math.min(Math.max(chance, 0), 0.999);        // 夹住 0/1，防除零
    return (otherBuckets * p) / (1 - p);
}
```

⚠️ **35% 对应的倍率是 2.692，不是直觉上的 2.1**（`1.35/1` 这类估法是错的）。
`1.35` 那种"倍率≈涨幅"只在目标概率接近基准时才近似成立。**别算，直接写概率**。

报给用户的表要带**三列**（均匀基准 / 上一版 / 本次），否则看不出这次改动的边际收益：

| 观察项 | 为什么值得报 | 本例 20%→35% |
|---|---|---|
| 目标档出现率 | 用户要的那个数，必须精确给 | 20.00% → **35.00%** |
| **决策点个数 / 局** | 代价在哪：无决策的档（本例 1 蘑菇盘）提上来，必然稀释"真正要做决定"的次数 | 3.200 → **2.600（−19%）** |
| **决策点个数分布**（0/1/2/…个的占比） | **均值会掩盖手感变化**。分布才看得出"近半数局只需 0~2 次抉择" | 0~2 个的局 24.2% → **46.6%** |
| 开局必败率 | 决定"看穿认输"这类元机制有多少表演机会 | 16.48% → **25.11%** |
| 相关结构长度（本例：最长连续 1 链 / 局） | 真正的难度来源往往不是"某档比例"，而是**它连成链的长度** | 0.703 → **1.175** |

报数字时**用精确值**（穷举 + 概率加权），不要用模拟估计 —— 省事又不会有人质疑口径。

**边际收益递减要主动说**：本例 20%→35% 用 −19% 的决策点只换来 +8.6pt 的必败率。
如果用户还想加"转机"，更该动的是**其它维度**（本例：盘数 `n` 的分布，盘子越多 1 链越长、判据越深），
而不是把目标档继续往上压到"点几下看结果"。

## 设计层要一起报的结论

最优 AI 一旦落地，游戏就变成**确定性谜题**：玩家一步走错就再也翻不回来。评估体验不能看"AI 强不强"，要看两个数：

```js
// 开局裁决 + 先手胜率 —— 精确算法：穷举全部盘面，按出盘概率加权
console.log('先手理论必胜率:', 0.8352);      // 本案例（基准均匀分布为 0.8583）
```

- 先手胜率高 → 玩家大部分局只要走对就能赢，任何失误立刻输 → 这是"找线"谜题，适合做学习/教学型原型
- 先手胜率接近 50% → 接近抛硬币，玩家会觉得 AI "赖皮"

**该给用户摆的杠杆**（不要擅自加）：① 出盘分布调参（本案例已用，见上一节）；② 按概率的次优走法做难度梯度（代价是放弃可证最优）；③ 复盘/教练模式（终局公布开局裁决）；④ 让先手可控，避免开局就判死刑的局。

### 条件性 UI 就是答案播报器

凡是"看穿 / 识破 / 猜对"这一类**玩家声明式**机制，UI 绝不能提前透露裁决：

| 坏设计 | 后果 |
|---|---|
| 按钮只在必败局显示 | 按钮的存在 = 答案 |
| 按钮文案随裁决变色变字（"看穿败局" / "放弃胜利"） | 玩家不需要思考，读文案即可 |
| 按钮颜色随裁决变化 | 同理，颜色也是信息通道 |

做法：**按钮常驻 + 文案中性 + 结算才算账**。猜错的惩罚（判负）本身就是平衡器，不需要靠隐藏按钮。
配套断言廉价且有力：**必胜局与必败局的按钮文案必须完全一致**（`textWin === textLose`），
以及"必胜局按钮同样可见"。这条断言同时守住了机制的价值和按钮的存在性。

## 本机踩坑

- **`node` 里 `/tmp/x.js` 会被解析成 `D:\tmp\x.js`**（Windows 下相对当前盘符），报 `ENOENT`。临时文件用 `os.tmpdir()`。
- Bash 工具启动时 PATH 被 shim 破坏，命令前需显式修复：`export PATH="/usr/bin:/bin:$HOME/.workbuddy/binaries/node/versions/<版本>:$PATH"`。
- 用 `node --check <抽出的脚本>` 做交付前语法校验（单文件 HTML 无法直接 `--check`）。
