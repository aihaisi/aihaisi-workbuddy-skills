# 抗自欺验证纪律

## 0. 这个技能解决什么

唯一命题：**如何不自欺地确认一件事是真的。**

它不教你「多测试」，它防的是这种情况：**你已经相信结论成立了，而事实并非如此。**
出问题的地方极少是「没测」，绝大多数是「测了，但那个测试证明不了它声称证明的东西」。

**读它的时机**
- 即将说出「验证通过 / 测试全绿 / 没问题 / 已完成 / 能跑」
- 正在写断言、自检脚本、发布前检查
- 要判断一个「看着不对」的现象是 bug 还是预期
- 用户问「你确定吗」

**不用读的时机**：纯信息查询、格式转换、已做过很多次的常规操作。

具体领域的验证手段（无头渲染、布局审计、音视频校验）在各领域技能里，本技能只提供**跨域判据**。

### 强度要匹配风险：三档审计尺度（用户明确要求，跨项目生效）

**用户原话**（2026-10-02 17:15）：**「能用就用，遇到问题了再查」—— 明确反对过度审计。**
触发场景：我①把「装 jq」当成"未经请求的环境变更"而拒绝执行，②又在某个返 `FAILED` 的探针上继续深挖细节。
用户两件事一起叫停：**装就装，别搞仪式；真出问题再查。**

**根因**：我把「审计」当成了**态度**（凡事必审、越细越显得谨慎），
而它本该是**按风险分配的成本**。后果双输 —— 用户等不到结果，我还在自证谨慎。

| 档 | 情形 | 做法 |
|---|---|---|
| **免审** | 官方发行 + 用户已指定 + 只读/幂等 + 可回退（装 CLI、装 jq 这类） | 装完报一句「装好了 + 来源 + 校验方式」，**不停下来等确认** |
| **轻审**（几分钟） | 来源可信但会写盘/改配置（装第三方 skill、写 `~/.` 配置） | 扫一遍敏感面（外传/提权/凭据/`shell=True`），一句话给结论，**不写报告** |
| **全审**（写报告） | 来源不明、要执行远程脚本、要动系统或密钥、不可回退 | 完整审计 + 报告 + **停下来等确认** |

**两条例外（不受"别过度审计"约束）**：① `curl … | bash` 这类**远程管道执行**必须全审（骗过第一层引导脚本是常态）；② 触碰**密钥 / 账号 / 外发消息**的动作必须确认 —— 出事的代价不对称。

**判断标准**：不是「我审了多少」，而是「**这次审的东西，风险高到需要它吗**」。
- 审完不停等确认 = **越权**（把自己的成本转嫁给用户）
- 风险不明却直接干 = **失职**
- 两者同源：**强度不匹配风险** —— 与本技能防的「验证不足」是同一个病的两端。

## 1. 判据清单（13 条）

### 1. 验证通道必须独立于被验证对象

**判据**：如果验证用的东西和被验证的东西，会因为**同一个错误**而一起「看起来正常」，这个验证等于没做。

**做法**：先问「这条通道本身会不会也错，而且是同一个错？」是的话换通道。
- ✗ 用 `git ls-files` 扫敏感信息 —— 它只列**已跟踪**文件，新增的未跟踪目录整段逃过扫描
- ✓ 发布后用 blob sha 与本地 `git hash-object` 逐字节比对，而不是信 git 的传输结果
- ✓ 对比两套实现的数值差异时，把对方的核心函数**逐字抄过来**跑同一批输入，而不是在浏览器里肉眼比数字
- ⚠️ **通道证明的命题必须和你要下的结论对齐**，否则"独立"也救不了你。实测：某付费服务上线后改价不生效，而业务路径**全绿** —— 接口确实返 402、账单头能解码、字段齐全，于是「服务是好的」被顺手当成「配置是新的」。但那条通道只证明**代码跑起来了**，一个字都没说**读的是哪份配置**。根因是配置加载把开发口径排在部署口径之前，而支撑这个顺序的前提（"部署平台会过滤 `.env*`"）从头到尾只是**假设，从未被观测**。
  ⇒ **「进程活着 / 代码是新版 / 配置是新版」是三个命题**，各自要有各自的通道。凡涉及配置生效，必须有一个能回传「**当前生效的配置文件 + 关键配置值 + 进程启动时刻**」的自证端点（`pid`/`uptime` 用来把"配置没生效"与"进程没重启"这两种不同病因分开）。
  ⇒ **症状指纹**：同一份自证输出里，**新值已经进了文件、生效值还是旧值** —— 这是读错文件的签名，既不是"没上传"也不是"没重启"，用「重新发布一次」是治不好的。

### 2. 先证明「检测器有效」，再看检测结果

**判据**：一个从来没抓到过东西的检测器，和「环境干净」长得一模一样。
**反过来同样致命**：一个永远返回结果（或对任意输入都返回同一个值）的查询，和「目标确实存在」也长得一模一样。

**做法**：声明「扫描通过 / 无命中」时给出**阳性对照**；用「查不到」来证明「不存在」时给出**阴性对照**。两个方向缺一不可。
- 阳性对照｜变异测试：把代码改回旧写法，断言**必须挂**（实测挂 5 条 → 断言有牙齿）
- 阳性对照｜造一个必然命中的输入，验证通路真的通（`rc=0` 才是真无命中）
- 阴性对照｜造一个**必然不存在**的输入，确认它返回「空 / 404 / 明确的不存在」，**而不是兜底结果**。
  实测：某市场搜索 API 对无匹配查询**照样返回热门列表**（搜一个随机串仍返回 dev-expert / tencent-docs 等），
  于是「搜不到」推不出「没上架」；另一条 `api.<host>/<ns>/<slug>` 对**任意路径**都返同一个 405（确定在架的对照组也是 405），
  该端点根本不具区分力。两处都差点被当成「没发布」的证据。
- ⚠️ **不要用 `cmd && echo 有命中 || echo 无命中` 判断扫描结果** —— 命令自身报错（参数写错）也会走 `||` 分支，把「根本没扫」伪装成「干净」。判据必须是**退出码**：`rc=1` 才是无命中，`rc=2` 是命令出错。
- ⚠️ **探针脚本自己也会制造假阴性**：实测某验签探针从 `_response` 内层取 `sign`（实际在**顶层**），于是对一个带签名的响应输出「响应中无 sign 字段」。⇒ 探针报「缺失/异常」时，**先核对探针自己的取值路径**，再怀疑被测对象。
- 凭据/密钥类验收（appId + 私钥 + 平台公钥）有专门流程：见 `references/credential-probe-playbook.md`（**第零步配对自检** + 三步法 + 单变量对照 + 兜底码陷阱 + **覆盖边界：平台侧业务资源 ID 无法自证，探针须自报「仍未覆盖」**）。

### 3. 空集恒真 / 静默失效

**判据**：遍历型断言在「什么都没遍历到」时恒真。

**做法**：任何 `filter(...).every(...)` 型断言，旁边必须有一条**正向存在性断言**（「确实录到了 N 条」）。
- 实例：录制桩把字段记成 `undefined` → 过滤结果为空 → `every()` 对空数组返回 true → 断言以「0 条硬边」通过
- 同类：桩漏字段、选择器没选中、数组被提前清空、分页拉空、接口返回空数组
- ⚠️ **平台/架构矩阵缺项 = 静默降级**：某工具的资产清单只列了 `darwin-x64/arm64`、`linux-x64/arm64`，**缺 `win32-x64`** → 在 Windows 上它不报错，只返回 `UNSUPPORTED`，**悄悄改用系统命令**（且不告诉你这条路径没被验证过）。
  ⇒ 看到「内置依赖管理」，先核对该清单**是否覆盖当前平台**；缺失项永远不喊，只会让上层走一条没人测过的路。

### 4. 断言管得住逻辑，管不住观感

**判据**：数值断言只检查你能想到的关系；你没想到的语义错误，它全绿。

**做法**：**几何 / 视觉 / 布局类改动，必须留下截图或真实渲染结果供人看。**
- 实例：参数语义混用把伽马叠成 1.707 → 画面过曝 + 暗部块状色带，而 **84 条断言全绿**
- 这是整套纪律里最重要的一条：**「断言全绿」是必要条件，不是充分证据**，不能单独作为可交付依据

### 5. 测试素材本身要能暴露差异

**判据**：素材能不能让「差异」显形？不能的话，测出来的「没差别」毫无意义。

**做法**：验证滤波 / 调色 / 压缩 / 渲染效果，必须用**细节丰富的真实素材**，不能用纯色或合成图。
- 实例：`eq` / `colorbalance` 在 SMPTE 纯色测试图上几乎看不出差别 → 差点误判成「滤镜无效」

### 6. 先隔离再归因；隔离必须固定随机源

**判据**：没做单变量隔离就归因，等于猜。

**做法**：逐个关变量、看异常是否仍在，把嫌疑范围砍到最小，**再**去读代码。
- 实例：「只留最上游 pass」一步排除了 8 个 pass 里的 7 个
- ⚠️ **隔离实验必须固定随机源**：时间驱动（`uTime`）或随机数驱动的效果，测试时必须**显式传入固定时间/种子**，否则同一输入两次抓取不可复现，隔离实验会得出**随机结论**
- ⚠️ **同一能力有多条实现路径时，一条挂了不等于能力挂了**：实测本机 node 的 `execFileSync` / `spawnSync` / `execSync` **全部报 EBUSY**（连 `cmd.exe`、node 自己都一样），据此得出「node 不能创建子进程」；补测**异步** `execFile` 立刻正常（而目标技能恰好走的异步路径）。
  ⇒ 报「整个能力不可用」之前，必须把该能力的**每种调用形态**都单测一遍 —— 从子类失败外推全集，是最容易骗过自己的那种归纳。

### 7. 取样区自己会撒谎

**判据**：你划定的测量区域里，有没有混进不属于被测对象的成分？

**做法**：报告任何数值前，先检查取样区边界。
- 实例：裁剪区混进 2px 的 UI 分割线 → 产生 ±190 的假跳变，**把真正的异常盖掉了**

### 8. 知识归位按「触发场景」，不按「发现场景」

**判据**：判断一条经验该放哪，问的是「我下次**在什么任务里**会用到它」，不是「它当初是怎么被发现的」。

**做法**：写完笔记 / 技能后，用触发场景复核一遍归属。
- 实例：4 节玩法设计层的内容被错记在 HTML 原型技能里，只因「是在测 HTML 时发现的」

### 9. 本机能跑 ≠ 别人能跑

**判据**：项目里的路径、版本号、环境假设，有几条只在你机器上成立？

**做法**：发布 / 交付前 grep 全量搜死路径与硬编码版本号；忽略规则按「能不能由脚本重建」定。
- 实例：脚本硬编码 node 版本号目录 + 指向个人技能目录的绝对路径 —— 本机全绿，公开即废
- **硬编码版本号是静默故障**：本机恰好装了那个版本，所以永远不报错

### 10. 没跑过的分支 = 没验证的代码

**症状**：自检全绿 + 平台验收通过，一到真实场景就崩。

**2026-10-02 实例**：某付费服务的 19 项协议自检全绿、密钥预检全绿、平台页面显示「接入成功」，
但第一笔真实收款时服务端返回 `HTTP 500`。根因是交付路径上一行裸变量
`if (order.fulfillStatus === FULFILLED …)`（应为 `FULFILL_STATUS.FULFILLED`）。
这行只存在于「已付款 → 交付」路径，而这条路径**从未被任何测试执行过** ——
上游沙箱一直卡在更早的一步，所以从没走到这里。

**判据**：逐个列出分支，问「这**一条**被执行过吗」。覆盖率百分比会说谎，
但"这个 if 的 true 分支从没跑过"是客观事实。

**做法**：
- 关键路径用**注入式 mock** 替换外部依赖，离线把整条链路跑一遍（不联网、不花钱、可反复跑）。
  Node 下可在 `require` 目标模块**之前**改它的 `prototype`，实例即继承该替换。
- **成功分支和失败分支都要跑到**。只测「返回 402」不测「付款后交付」，等于没测 ——
  而恰好那条分支才是收钱的路径。
- 「接入成功 / 验收通过 / 部署成功」**不能替代执行证据**：它验的是配置与握手，
  不是你那条业务分支。页面绿 ≠ 你的代码对。
- 修完别只跑新加的断言 —— **再单独跑一遍失败分支**，确认拒绝逻辑真的拒绝了
  （兜底逻辑最容易把校验变成恒真）。

### 11. 不把易得指标当 KPI

**判据**：你报告的数字，是「事情变好了」还是「数字容易量」？

**做法**：指标往反方向走时**照实报**，并说明真实收益在哪。
- 实例：技能库合并后字节数反而 **+16%**（新增了导航层），真实收益是「少入口 + 无重复」 —— 不能说成「体积优化了」

### 12. 跨通道的能力不能互相推论

**判据**：你验证的是 A 通道，结论却说的是 B 通道吗？

**2026-10-03 实例**：某 Skill 包用官方 CLI 的 `publish --dry-run` 校验通过，
被顺口说成「这个 zip 平台认（网页向导也认）」。但 dry-run 只证明 **CLI 侧**校验器通过，
**网页向导是否接受同一个 zip 根本没跑过** —— 两句之间隔着一个没验证的假设。

**为什么危险**：这条不像"断言失败"那样会报错。它把「局部证据」放大成「全局结论」，
而且听起来完全合理 —— 同一个格式、同一个平台、同一个包，凭什么不认？
但"凭什么不认"不是证据。

**做法**：
- 结论里的每个通道名，问一句「**这个通道我跑过吗**」。没跑过就降级措辞为「推断 / 预期」，
  并显式标注未验证 —— 而不是用肯定的语气带过。
- 同一能力在不同入口（CLI / 网页 / API / 不同客户端）通常有**独立校验器**，
  通过一个不代表通过另一个；反过来，一个报错也不代表另一个会报错。
- 用户可能因此跳过自查（既然"平台认"，我就不用自己看了）⇒ 措辞不严谨会**转嫁风险**。

### 13. 先验证「前提能力」存在，再投入实现

**判据**：你要实现的东西所依赖的那个**能力 / 权限 / 接口**，确认存在了吗？

**2026-10-03 实例**：为回答「怎么对账」，先写了交易查询工具 `tools/query-trade.js`，
跑完才发现这个 appId **根本没有 `alipay.trade.query` 权限**（恒返 `40006 isv.insufficient-isv-permissions`）—— 工具白写。
正确顺序是**先花一分钟确认能力存在，再决定要不要造工具**。

**为什么危险**：能力缺失的报错**长得像配置错误** —— 同族的 `40002 isv.invalid-signature` 就真是密钥问题，
两者只差一个码，很容易被引去重配密钥（与判据 2 里「把公钥是对的误报成公钥不对」是同一族的诱饵）。
**证伪靠验签**：同一请求的**响应验签是通的** ⇒ 认证链路正常，纯粹是接口未开通。
⇒ **验签通过 + 业务码拒绝 = 身份对、能力缺**，别再动密钥。

**做法**：动手前用**最便宜的一步**确认前提 —— 官方接口清单 / 账号权限列表 / 一个最小请求。
成本排序是「先便宜后昂贵」，不是「先实现后验证」。
- 与判据 2 的分工：判据 2 问「检测器有没有区分力」，这条问「**被测能力本身存不存在**」。
- ⚠️ 未开通 / 无权限这类**能力缺失**在启动、自检、认证探针上**全部照过**
  （同 `references/credential-probe-playbook.md`「边界」节：平台侧业务资源 ID 无法自证）——
  只能靠能力清单或一笔真实业务确认。

## 2. 四个收尾清单（动手前 / 发布前 / 写完断言后 / 给结论前）

### 动手前（分档）
- [ ] 这次操作该走哪一档？（免审 / 轻审 / 全审，§0 成本纪律）
- [ ] 我是不是把「免审 / 轻审」的活干成了「全审」，在没风险的地方搞仪式？
- [ ] 依赖的能力 / 权限确认存在吗？（判据 13）

### 发布 / 交付前
- [ ] 阳性对照做过吗？（判据 2）
- [ ] 死路径、硬编码版本号 grep 过了吗？（判据 9）
- [ ] 忽略规则是按「能否由脚本重建」定的吗？（判据 9）
- [ ] 用独立通道核验过产物一致性吗？（判据 1）

### 写完断言后
- [ ] 有没有空集恒真的断言？（判据 3）
- [ ] 变异一下，断言真的会挂吗？（判据 2）
- [ ] 涉及几何/视觉的，截图留存了吗？（判据 4）
- [ ] 时间/随机驱动的部分固定了吗？（判据 6）

### 给出结论前
- [ ] 我的证据是**证明了**这个结论，还是只**没能反驳**它？（判据 1、4）
- [ ] 若结论是「没有 / 不存在 / 没上架 / 找不到」——我的检测器在目标**真不存在**时会给出什么？它给不出区分，我就不能下这个结论（判据 2、3）
- [ ] 结论里点到的每个通道（CLI / 网页 / API / 客户端）我都跑过吗？没跑过的降级为「推断」并标注（判据 12）
- [ ] 测量区域干净吗？（判据 7）
- [ ] 有没有我没检查、但可能让结论翻转的地方？

## 3. 边界与关联

- 本技能是**判据集**，不是流程引擎。各领域的具体验证手段见：`references/credential-probe-playbook.md`（第三方平台凭据/密钥验收三步法 + 可验证性边界）、`html-prototype-verify-ship`（冒烟 / 真渲染 / 发布）、`webgl-postproc-pipeline`（管线与隔离实验）、`ffmpeg-video-pipeline-pitfalls`（音视频校验）、`gameplay-design-verification`（玩法可证伪）、`workbuddy-skills-repo-sync`（技能库核验与脱敏扫描）。

## 4. 一句话

**「测过了」不是结论；「检测器有效 + 被测对象独立可测 + 我亲眼看过」才是。**
