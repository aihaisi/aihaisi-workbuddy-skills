# 凭据 / 密钥类验收：实测三步法

**适用**：第三方开放平台（支付、云、地图、短信…）给了你 appId + 私钥 + 平台公钥 + 账号，
你要回答「这套配置到底能不能用」。这属于判据 1（通道独立）、判据 2（检测器有效）的应用。

---

## 为什么不能只做离线配对自证

离线自证（从私钥导出公钥、与手上的「应用公钥」比对）**只能证明这两把是一对**。
它证明不了：

- appId 是否有效
- 网关地址是否对
- 签名参数拼装 / 时间戳格式 / 编码是否正确
- **手上那把「平台公钥」是否真是平台的公钥**（这条最致命：用错公钥运行时只报 `invalid-signature`，
  而所有人的第一反应都是「私钥格式问题」——归因链就此跑偏）

⇒ 必须用**平台返回的真实签名**做闭环，否则整个验证是自嗨。

---

## 三步

### 第零步：配对自检（先做，成本最低）

```
node tools/app-key.mjs check   # 从私钥导出 SPKI 公钥 → 与登记的「应用公钥」逐位比对 + 签名验签往返
```

为什么值得单列一步：**「私钥不配对」在配置阶段完全不报错**，只在你第一次调网关时才炸；
而那个现场信息（`isv.invalid-signature`）又会把人引向「私钥格式不对」这条错误归因。
更常见的是**两套密钥混用** —— 从沙箱切生产时，把「生产 appId + 生产公钥 + **沙箱私钥**」拼在一起（实测踩过）。

廉价且判别力强的三个设计：

| 设计 | 作用 |
|---|---|
| **只输出公钥指纹**（SHA256 前 16 位），永不回显私钥 | 自检可以交给别人跑、可贴进对话/工单，密钥不出本机 |
| 不配对时**交叉比对另一套已知密钥** | 自动**归因**——"你这把私钥其实是沙箱那套"，比干说 MISMATCH 有用得多 |
| **内置阴性对照**（拿另一套已知密钥自对自，必须 MATCH） | 证明检测器本身没坏，否则"报错"可能只是检测器的问题 |

> 配对自检只回答「这两把是不是一对」，回答不了 appId / 网关 / 拼装是否正确
> ⇒ **不能替代下面三步**，但它把最廉价、最高频的一类故障挡在门口。

### 第一步：打一发「认证先行、业务必错」的请求

挑一个**必然产生业务错误、但认证在校验业务之前**的通用接口（如交易查询、订单查询），
传入一个必然不存在的业务标识。

| 响应 | 含义 |
|---|---|
| 业务码 + 「不存在」类子码（如 `ACQ.TRADE_NOT_EXIST / 交易不存在`） | ✅ 认证链路全通，只是这单没有 |
| `40002 / isv.invalid-signature` | ❌ 签名/密钥问题（**这就是密钥不配对的正常长相**） |
| HTTP 404 / 返回 HTML 页面 | ❌ 网关地址错，或 method/appId 不被路由 |

### 第二步：单变量对照，证明探针有区分力

固定其他一切，只改一个变量，跑 3 组以上。**响应必须分化**：

| 组 | 改动 | 期望（有区分力） |
|---|---|---|
| 基线 | 都对 | 正常的业务侧响应 |
| B | 只改 appId | 与基线不同（404 / 不同错误码） |
| C | 只改私钥（现场随机生成一把） | `isv.invalid-signature` |
| D | 只改 method（编造一个） | 与基线不同（未知方法通常返回 HTML 页） |

⚠️ 若 B/C/D 与基线**返回完全相同**，说明网关对什么都照单全收，
此时第一步的结果证明不了任何事 —— 探针无区分力，结论作废。

### 第三步：用平台公钥验平台返回的 `sign`

这是「公钥真伪」的**唯一硬证据**，也是整个流程里最值钱的一步。

- 验签对象 = 响应里 `<method>_response` 节点的内容（剔除 `sign`）
- ⚠️ 先确认 `sign` 在**哪一层**：常见是**顶层**，不在 `_response` 内部（取错层会恒判「无 sign 字段」）
- ⚠️ 重序列化 vs 原串切片：先实测「parse 后重新 stringify」与「原串切片」是否**逐字节一致**，
  一致才可放心用标准写法；不一致必须用原串切片，否则会出假阴性
- ⚠️ **但真正的坑是「构造规则本身就错」，不是重序列化**（2026-10-02 实测）：
  **嵌套响应**的正确验签对象是 `<method>_response` **节点的原串本身**（`{"msg":…,"code":…}` 这段文本），
  **不是** `外层key=JSON(内层)`，也**不是** `内层字段按 k=v 拼接`。实测这三种错误构造在**生产与沙箱双双**恒判失败，
  而响应完全合法 —— 症状会把人误导到「平台公钥不对」，跑去后台白白重配密钥。
  ⇒ **嵌套与扁平两种形态各写一个离线 fixture 测试**（本地生成密钥对自签自发），否则改了没人发现。
- ⚠️ **算出来却不参与判定的检查 = 假安全信号**。本案 `responseVerified` 被计算、被打印，
  却从未进入任何分支条件 —— 于是错误长期潜伏，诊断时还给出错误归因。
  ⇒ 验证结果必须有**明确的消费点**：拒绝交付 / 告警 / 断言，三者至少有一个。
- ✅ **必带阴性对照**：换一把无关公钥必须验不过。没有阴性对照的 PASS 可能是恒真

## 边界：这套探针**验不了**什么（探针必须自己声明）

配好密钥 ≠ 全配好了。实测里同属「生产配置」的两类值，可验证性完全不同：

| 类别 | 例子 | 能否用 API 凭据自证 |
|---|---|---|
| **密钥 / 身份类** | appId、应用私钥、平台公钥、网关地址 | ✅ 能 —— 就是上面三步干的事 |
| **平台侧登记的业务资源 ID** | 服务市场 `serviceId`、商品/模板 ID、后台登记价 | ❌ **不能** |

业务资源 ID 既不参与你的签名校验，也不被认证类接口读取 ⇒ 写错时**启动、自检、认证探针全部照过**，
只在真正走业务（收银 / 下单）时才炸，而那时现场信息离配置现场已经很远
（同族的静默失效：平台登记价与账单价不一致，只报一个官方文档里查不到的 `SERVICE_PRICE_MISMATCH`）。

两条纪律：

1. **探针的最终输出必须显式列出「本次覆盖范围」与「仍未覆盖」** ——
   `preflight` 结尾那行「仍未覆盖：产品是否已开通、serviceId 是否正确、真实收银流程」就是正确示范。
   否则一句「✅ 全部通过」会被读成「整条链路都对」（这正是判据 1 的失效形态：通道证明的命题 ≠ 你要下的结论）。
2. 这类 ID 只能靠**平台自己的登记表**（控制台页面、带账号态的资源列表接口）或**一笔真实业务**确认，
   别指望自制探针 —— 自制探针在这里的判别力是零，不是弱。

## 高发陷阱

1. **兜底码 ≠ 故障。** `40004 / SYSTEM_ERROR / 系统繁忙` 通常是网关对未预期异常的**兜底**，
   用假凭证调业务接口得到它是**预期行为**，不能据此判断「产品没开通 / 环境坏了」。
   同文案可能是另一个码（如官方码表里「系统繁忙」= `20000 / isp.unknow-error`）——**看码，不看看文案**。

2. **探针脚本自己会有 bug，且是假阴性方向。** 实测：从 `_response` 内层取 `sign`（实际在顶层），
   于是脚本对一个带签名的响应输出「响应中无 sign 字段」。
   ⇒ 探针输出「异常/缺失」时，**先核对探针自身的取值路径**，再怀疑被测对象。
   这也意味着：探针须与前述单变量对照一起使用，单凭一次输出不足以下结论。

3. **结果不稳定要重跑确认。** 同一请求两轮给不同结果（一次 200 JSON、一次 404 HTML）
   说明存在限流/抖动/批次效应 ⇒ 必须重复实验（≥3 次）后再下结论，不能取单次。

4. **平台说「要发一笔真实交易才算验证」，不代表你真得先花钱。**
   官方验收清单常写成「发起一笔真实交易」——但那笔交易验的是**整条业务闭环**；
   链路里最易错的那部分（appId / 私钥配对 / 平台公钥真伪 / 网关地址）**完全可以用「认证先行、业务必错」的
   请求免费验掉**。把昂贵步骤放在最后，先用零成本探针把配置类故障清零，能省掉最难排查的一类返工。
   同理：**「可选」项要真的当可选**——先确认你的实现里根本不存在那项（例如服务端本就没有异步回调），
   比硬凑一个能过审的假实现更正确。

5. **验签通过的响应也要看「业务码是不是兜底码」**（见上文陷阱 1），
   两者结合才是完整判据：**签名可信 ∧ 业务码可解释**。

6. **「没开通 / 没权限」会被伪装成「配错了」。** 同一族报错里，`40002 isv.invalid-signature`（真·密钥问题）
   与 `40006 isv.insufficient-isv-permissions`（接口根本没开通）长得很像，
   而后者**启动、自检、认证探针全部照过**（认证本身是通的）。
   ⇒ 判据：**响应验签通过**却返业务拒绝码 = **身份对、能力缺**，**别再去重配密钥**。
   实测把 `trade.query` 的 `40006` 误当"配置/密钥"问题排查过一轮，纯属浪费。
   ⇒ 动手前先核对该 appId **开通了哪些接口**（能力清单），别等写完工具才发现它不可用（判据 13）。

## 脚本骨架（Node，零依赖，可直接改）

```js
// 读凭证（从暂存文件读，不写死在脚本里）
const env = {};
for (const line of fs.readFileSync(process.argv[2], 'utf8').split(/\r?\n/)) {
  const m = line.match(/^([A-Z0-9_]+)=(.*)$/);
  if (m) env[m[1]] = m[2].trim();
}
const priv = crypto.createPrivateKey({ key: Buffer.from(env.APP_PRIVATE_KEY, 'base64'), format: 'der', type: 'pkcs8' });

// 签名：参数按 key 升序拼 k=v&k=v（剔除 sign 与空值），SHA256withRSA → base64
const content = Object.keys(params).filter((k) => k !== 'sign' && params[k] !== '').sort()
  .map((k) => `${k}=${params[k]}`).join('&');
const sign = crypto.sign('sha256', Buffer.from(content, 'utf8'), priv).toString('base64');

// 验平台响应：先确认 sign 层级；阴性对照用现场生成的无关公钥
crypto.verify('sha256', Buffer.from(payload, 'utf8'), platPub, Buffer.from(respSign, 'base64'));
```

- 时间戳格式按平台要求（支付宝是 `yyyy-MM-dd HH:mm:ss`，**不是 ISO**，且要北京时间）
- 私钥永不打印；凭证从暂存文件读、不进 git 仓库

`probe_verify_signature.mjs`（公钥验签 + 阴性对照）、`probe_aipay_method.mjs`（重复实验）。
