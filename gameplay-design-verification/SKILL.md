# 玩法设计的可计算验证

## 0. 在开发流程里的位置

| 阶段 | 问题 | 判据 | 详细做法 |
|---|---|---|---|
| **设计期**（写 UI 之前） | 这个玩法**有没有**决策空间？ | 规划增益 / 技能表达 / UX 体检 | `references/design-criteria.md` |
| **实现期**（原型跑起来后） | AI **是不是真的**最优？ | 走法最优性 / 端到端对账 / UI 门控 | `references/optimality-verify.md` |

**核心原则：别用直觉回答"有没有深度""聪不聪明"，换成可计数的量。**

**不适用**：有隐藏信息 / 随机事件 / 实时动作的游戏（搜索树爆炸，改用启发式 + 胜率评估）。

### 已知边界（写结论时必须原样带上）

1. **这套方法能证明"没有决策空间"，不能证明"好玩"。** 它是否决工具，不是验收工具。
2. **模拟里的"玩家技能参数"是自由参数，没有真人数据。** 它的价值是给出**校准框架和敏感度方向**，不是精确预测。
3. **判据七有分辨率边界**：对「动作会永久改变世界结构」的玩法，交换散度会给出**假阴性**。判据测不出区别时，**先怀疑判据的分辨力，再怀疑玩法** —— 否则会用它砍掉一个好玩法。这类玩法改用**不可逆动作比例**。
4. **判据八的"能当杠杆"不等于"该当主杠杆"**：限时惩罚"慢"，而如果"慢"正是被测的技能，限时就在删掉你要考的东西。

### 相关技能（分工，别重复造）

- **本技能管「设计与算法层」**：这个玩法有没有决策空间、AI 是不是真的最优。
- **单文件 HTML 原型的交付期验证**（DOM 桩 + node `vm` 的搭法、无头 Chrome 布局、发布上线）走 **`html-prototype-verify-ship`**。本技能讲"断言什么"，那份讲"怎么把页面脚本加载起来断言"。
- **实时渲染 / WebGL 管线的验证**（着色器编译、pass 间一致性）走 **`webgl-postproc-pipeline`**。

# 一、设计期：这个玩法有决策空间吗

## 1.1 为什么必须做

**「资源转化链 + 手牌跨回合保留」这类看着合理的设计，极大概率没有决策空间。** 作者的直觉会被"资源""取舍""规划"这些词骗过，但跑一遍分布立刻现形。

真实案例（休闲矩阵第 4 模块）：连续三版设计被枪毙，全是纸面推演发现不了的：

| 版本 | 结构 | 规划增益 | 技能表达 | 死因 |
|---|---|---|---|---|
| v1 | 回合制、每回合补 2 张牌、手牌跨回合保留 | +0.0% | 0% | 资源无限增长 → 无稀缺。`greedy` 与 `planner` 分布**逐字节相同** |
| v2 | 补 1 张 + 手牌上限 8 + 每回合二选一 | +0.9% | 0% | 资源可再生 → 当前决策不改变未来可行集 = 套利非规划 |
| v3 | 牌一次性发完 + 分轮揭示 + 规模奖励 | +31.4% | +12.5% | 最优策略退化为 (0,0,3)：前两轮空转，**忍耐游戏** |

成本：3 次模拟 ≈ 半小时。若走到实现阶段才发现，成本是数周。**结局：这个范式被整个放弃，第 4 槽位换成「落块堆叠（不可撤销的状态累积）」。**

## 1.2 四层策略框架（核心工具）

对同一个玩法实现四种打法，跑分布对比：

| 策略 | 定义 | 作用 |
|---|---|---|
| **random** | 随机决策 + 执行噪声 | 下界（真实玩家最差水平） |
| **greedy** | 只优化当前回合，能做的都做 | **无规划基准线** |
| **planner** | 引入前瞻参数（阈值 / 预算比例 / 搜索深度）并**扫描其最优值** | 玩家可达上界 |
| **oracle** | 全知：开局就知道全部未来信息，做全局最优 | **理论天花板** |

关键：**planner 的参数必须扫描并取最优**，而不是拍一个值。扫描过程本身会暴露"最优策略长什么样" —— v3 初版的最优解 `(0,0,3)` 就是从组合空间搜索里搜出来的，这是拍脑袋绝对想不到的。

## 1.3 三项指标与判据

| 指标 | 算法 | 判据 |
|---|---|---|
| **规划增益** | (planner 均值 − greedy 均值) / greedy 均值 | < 5% ⇒ 无决策空间，重设计；> 10% ⇒ 有深度 |
| **技能表达** | 把一个"决策质量"参数从差扫到好，看得分跨度 | 跨度 < 8% ⇒ 高手新手一个样，玩法不表达技能 |
| **UX 体检** | 统计最优策略**每回合/每轮的实际产出量** | 产出集中在单一阶段 ⇒ 其余时间玩家在空转 ⇒ 不成立 |

**UX 体检最容易被忽略，也最致命。** 一个玩法可以同时拥有 +31% 规划增益和 0% 技能表达，而它的最优策略是"前 2/3 时间什么都别做" —— 数据好看，做出来是灾难。

```python
# ① 规划增益
gap = (mean(planner) - mean(greedy)) / mean(greedy)

# ② 技能表达：把"决策质量"从差扫到好
for jit in (0.00, 0.10, 0.25, 0.45, 0.70): ...

# ③ UX 体检：最优策略的每轮产出（**必须做**）
trace = []
run_n(..., trace=trace)          # play() 内记录每轮实际完成的动作数
av = [sum(h[i] for h, _ in trace) / len(trace) for i in range(ROUNDS)]
```

**`seed` 里必须包含参数盐**（`seed + tier*41 + int(jitter*100) + ...`），否则不同参数格共用同一条随机流，分布对比会被污染。参数是 tuple 时用 `sum(pr)*7` 之类的哈希。

## 1.4 十条判据速查（细节见 references/design-criteria.md）

**先按这道顺序问，别跳步** —— 七 → 八 是有顺序的：可交换性便宜、能先验推、出 0 就是死刑；它过了再花力气测前沿形状。

| # | 判据 | 一句话判据 | 展开 |
|---|---|---|---|
| 一 | 资源供给四象限 | 只有「**可再生 + 稀缺**」这一格能产生真实跨回合决策 | 计划性玩法的入门闸 |
| 二 | 轮次相关性不能过强 | 「第 N 轮」与「价值高」强相关 ⟹ 最优解退化为「等」 | 代价：重叠会降低规划增益 |
| 三 | **同范式连续三次失败 ＝ 范式问题** | 问「这一版的失败原因，和上一版是同一个吗？」 | **本方法最重要的元判据** |
| 四 | 评分锚点决定曲线形状 | 锚在**稀有事件** → 悬崖；锚在**持续量** → 阶梯 | 接经济/评分系统时必须管 |
| 五 | 步数 ≠ 时长 | 先定真实时长，再按每步耗时反推步数，用那个步数跑分布 | 否则一直得到"这玩法很好"的假结论 |
| 六 | 该不该打开被锁死的维度 | 取值敏感度 + 技能梯度增量 + **失败态是否保留** | ② 两侧必须共用同一评估函数 |
| 七 | **动作可交换性** | 「两个动作交换顺序后局面一样吗？」一样 ⟹ 决策空间为零 | **推理/解谜类的第一道闸**（有适用边界，见下） |
| 八 | 成本-质量斜坡 | 数帕累托前沿的点数：点多连续 → 限时制造真权衡；只有孤立几点 → 限时只做 0/1 筛选 | "限时能不能把知识变成技能"是可算的 |
| 九 | 用七+八给候选范式打分 | 换量尺：改变世界型玩法读**不可逆动作比例** | 选型阶段用 |
| 十 | **表态次数 ≠ 思考负载** | 决策点个数是操作步数，不是深度 | 两个旋钮性质可能相反 |

### 三条最容易用错的地方

**① 判据七有适用边界，会用错量尺把活玩法判死。**
判据七只对「动作集合固定、动作之间靠状态耦合」的玩法有效（资源分配、约束累积、查证推理）。对「动作会**永久改变世界结构**」的玩法（推箱、拆卸、建造、地形改造），交换散度**没有分辨力**（推箱 0.0~0.3% vs 证词网 0.00%，读数无法区分）。这类玩法改用 **不可逆动作比例**：> 0 才有决策空间，== 0 就是判据七说的死局。**必须配对照组** —— 单独说「16.2%」不构成任何主张。

**② 判据八的"能当杠杆" ≠ "该当主杠杆"。**
限时惩罚的是「慢」，而**如果慢正是被测的那项技能，限时就在把你要考的东西删掉**（倒计时一上来，玩家从"想清楚再推"退化成"先推了再说"）。
> **正确分工：预算类约束（步数/推数/资源上限）当难度杠杆** —— 它精确、可从关卡自身推出、能写成断言；**时间只当节奏与防挂机的兜底**，全档同构。

**③ 两个旋钮性质相反，加"转机"要挑对那个。**

**判据十给的结论**：抬高特殊局面概率（`P(a_i=1)`）是**零和** —— 转机↑ 但思考负载被稀释；放宽结构规模（盘子数上限）是**正和** —— 两头都涨。
⟹ **加转机优先动「结构规模」，而不是「特殊局面概率」。**（完整实测对照表与代价账单见 `references/design-criteria.md` 判据十。）
⚠️ 硬约束：扩规模会让**验证成本爆炸**（`n≤6` 是 55986 盘面，`n=7` 是 2.8e5、`n=9` 是 1e7），扩之前先想清楚验证怎么降级，并诚实标注"降级后就不再是证明"。

**不建议的第三条路**：让 AI 按概率走次优解做难度梯度。它会摧毁"AI 每步唯一最优、输了就是你的问题"这个最硬的设计说服力 —— 玩家无法区分"我输是因为 AI 乱走"和"我走错了"。这是换赛道，不是调参。

# 二、实现期：AI 真的最优吗

## 2.1 核心原则：别急着写 AI，先证结构性质

**绝大多数取物类博弈都有"只剩一个变量"的化简。** 找到它，AI 就从"搜索"退化成"查表"，最优性也变得可证。

验证顺序（缺一层就会误判）：

| 层 | 做什么 | 证明什么 |
|---|---|---|
| ① 结构性质 | 博弈树归纳，找必败态的形态约束 | 必败态长什么样（往往能推出"走法唯一"） |
| ② 闭式解 | O(n) 递推算胜负 + 走法 | 可实现的策略 |
| ③ 逐状态交叉验证 | 暴力 DP vs 闭式解，穷举所有可达状态 | 闭式解没写错 |
| ④ 自对弈端到端 | 双方都走最优，终局胜者 == 开局裁决 | **走法选择**（不只是胜负判断）是对的 |
| ⑤ 新旧对战 | 旧 AI vs 新 AI 胜率 | 量化"修好了"而不是"感觉修好了" |
| ⑥ **官方样例对拍** | 题面自带样例 vs 求解器输出 | **外部权威**校准 |

**⑥ 是最容易被漏掉、也是唯一真正独立的一层。** ①②③ 都只是在跟"自己的暴力解"对账，两者可能同时错（对规则的理解本身就偏了）。原型的题目若出自公开题库（洛谷 / Codeforces / 牛客…），把题面样例**连同期望赢家**硬编码进验证脚本：

```js
const LUOGU_SAMPLES = [                       // 来源：洛谷 U145698 题面样例
  { a: [1, 1, 1],    expect: 'Elaina' },
  { a: [1, 2, 1],    expect: 'Fran'   },
  { a: [3, 4, 5],    expect: 'Elaina' },     // 注意样例要连"期望赢家"一起抄，
  { a: [1, 2, 1, 2], expect: 'Fran'   },     // 只抄输入等于没对拍
  { a: [8, 1],       expect: 'Elaina' },
];
```

顺手把题面的**数据范围**也抄进自对弈的随机参数（如 `1 ≤ n ≤ 50, 1 ≤ a_i ≤ 1e6`），这样"穷举验证的小值域"和"自对弈的大值域"刚好覆盖题面的完整边界。

### ① 的实战价值：一条定理省掉整段代码

本案例从"必败态的形态约束"推出：**当前盘剩余 m ≥ 2 ⇒ 轮到的人必胜**，进而 **m == 1 必败且走法唯一** ⟹ 最优 AI **不存在** "必败时怎么挣扎"的自由度 —— 任何 `if (必败态) 随机取` 的分支都是错的，**"必败时随机捣乱等玩家失误"是伪需求**。（完整推导与"想给玩家机会该怎么做"见 `references/optimality-verify.md`。）

## 2.2 抽取而非复制（最关键的一步）

把求解器包在标记块里，**验证脚本从交付文件抽出这段代码执行**：

```js
/* ==== MUSHROOM-SOLVER BEGIN ==== */
function computeLosingFlags(plates) {     // lose[j] = 轮到你从第 j 盘开始处理时必输吗
  const n = plates.length;
  const lose = new Array(n + 1);
  lose[n] = true;                         // 盘面已空 → 无子可取者判负
  for (let j = n - 1; j >= 0; j--) lose[j] = (plates[j] === 1) ? !lose[j + 1] : false;
  return lose;
}
function analyzePosition(plates, activeIndex, remaining) { /* 返回 {canWin, move} */ }
/* ==== MUSHROOM-SOLVER END ==== */
```

```js
const html = readFileSync('index.html', 'utf8');
const blk = html.match(/\/\* ==== MUSHROOM-SOLVER BEGIN ==== \*\/([\s\S]*?)\/\* ==== MUSHROOM-SOLVER END ==== \*\//)[1];
const { computeLosingFlags, analyzePosition } = new Function(blk + ';return {computeLosingFlags, analyzePosition};')();
```

否则你测的是副本，上线的是另一版 —— **"测试全绿但线上还是错"**。

## 2.3 必写的四类断言

```js
// 1) 胜负判断逐状态一致
if (info.canWin !== bruteWin(i, m)) fail(`胜负判断错误 [${a}] i=${i} m=${m}`);

// 2) 走法最优性：这一步必须把对手送进必败态（比"胜负对"更强的断言）
const oppLoses = info.move === m
  ? (i + 1 >= a.length ? false : win(i + 1, a[i + 1]))
  : win(i, m - info.move);
if (oppLoses !== false) fail('走法非最优：留给对手的是必胜态');

// 3) 必败态走法唯一性（守住"不存在抉择空间"这条定理）
if (!info.canWin && m !== 1) fail(`必败态但 m=${m} > 1，出现意料之外的抉择空间`);

// 4) 大值域自对弈：双方都走最优，胜者必须 == 开局裁决
//    n=50、a_i=1e6 的随机盘面跑 2000 局（暴力 DP 跑不动，只能靠自对弈兜底）
```

断言 ② 是重点：**只验"谁赢"会漏掉"能赢但走错"。** AI 最优性必须验到走法层面。

**排查信号：如果 AI 的判据里不出现「当前堆还剩几个」，它几乎一定错了。**
旧判据用**绝对下标奇偶**（`firstGT1 % 2`）判胜负，而正确判据是**相对于盘尾的距离** —— 绝对下标一路错，且 m 不参与判断，而 m ≥ 2 必胜是第一条定理，判据里不出现 m 本身就已经暴露了问题。

## 2.4 第三层：UI 门控也要单独测（穷举测不到）

求解器最优 ≠ 玩法正确。规则门控（"什么条件下允许点什么"）是**状态机**，不在求解器的状态空间里，必须把整段 `<script>` 用 DOM 桩跑起来：

```js
const pageSrc = html.match(/<script>([\s\S]*?)<\/script>/)[1];
globalThis.document = { getElementById: (id) => cache(id) || (cache[id] = mkEl()), createElement: (t) => mkEl(t) };
globalThis.setTimeout = () => 0;               // 关掉 AI 自动回手，测试自己驱动
new Function(`${pageSrc}
globalThis.__api = { initGame, playerMove, playerSurrender, aiTurn, renderBoard,
  setPlates: (a) => { plates = a; },           // 覆盖随机出盘，换确定性盘面
  btn: () => document.getElementById('btn-surrender'),
  moves: () => moveCount };`)();
```

三个坑：

- `let` 在 `new Function` 体里是函数作用域，**必须靠末尾追加一行显式导出**（`vm` 同理）
- DOM 桩要**按 id 缓存同一个对象**，否则 `renderBoard()` 改的和你断言的不是同一个元素
- `setTimeout` 设 no-op 后 AI 不会自动回手，用 `aiTurn()` 手动驱动 → 完全确定性

### ⚠️ 顺序依赖的守卫函数：一行就能让分支变成死代码

```js
function isLosing() { if (isGameOver) return false; return !analyze().canWin; }
function surrender() { isGameOver = true; if (isLosing()) judgeWin(); else judgeLose(); }  // 判胜永远不可达
```

**判据：凡是"先置状态、再查询"的调用序列，都要断言两个分支都可达。** 修法双管齐下 —— 查询函数保持纯粹（不留外部状态守卫）**且**把查询提到置位之前。配套断言：分别喂一个"该判胜"和一个"该判负"的输入，断言两种结算都出现过。**只测一种等于没测。**

# 三、断言与变异测试纪律（两侧共用，只此一份）

## 3.1 四种失效模式

前三种"永远通过"，第四种相反"无行为变更也失败" —— 两个极端都要校准。

| 缺陷 | 长什么样 | 后果 | 正确做法 |
|---|---|---|---|
| **恒真式断言** | 断言"配置与自身常量自洽"（如 `ns.length === PLATE_SPAN`）；或拿配置常量去断言配置常量（`pOf(1) === spawn.ONE_MUSHROOM_CHANCE`） | 把上界从 3 改成 2 也照样通过 | 钉**字面量**契约 `[3,4,5]` / `0.35`，并在消息里说明"有意修改时请同步文档" —— **这份摩擦是刻意的** |
| **硬编码 ✓ 的报告行** | `console.log('结果: ✓ 与求解器完全一致')` | 断言失败了报告仍显示 ✓ —— **比没有报告更糟** | 报告行必须由真实结果驱动（存一个 `ok` 布尔，据它渲染 ✓/✗） |
| **统计抽样的概率断言** | 抽 10 万次随机数估 `P(a=1) ≈ 35%`，容差 ±2% | 方差导致偶发变红；为不抖动只能放宽容差 → 又失去灵敏度 | 把抽样器写成**纯函数** `pick(rand)`，验证器在 `[0,1)` 上**穷举网格**，把分布精确算出来 |
| **过拟合断言** | 断言"配置里的权重数组**恰好**是 `[0.7, 1.6, 1.6, 1.6]`" | 一个**无行为影响**的清理动作（权重整体减半）会让测试变红 —— **误伤** | 断言**可观察行为**：归一化后的**概率**落在 `[10%,16%]`、值域等于 `[3,4,5,6]` |

**第三条的连锁好处**：抽样器一旦是纯函数，产物侧也能精确算设计指标（穷举全部盘面按概率加权），报告里给的数字从"抽样估计"升级成"精确值" —— 而这两者会差出小数点后一位（85.4% vs 85.83%）。

**第一 / 四条是一对**：恒真式太松（永远绿），过拟合太紧（无行为变更也红）。两侧都要用变异测试校准 —— 所以变异清单里**同时要有"该抓的"和"该放的"**。

## 3.2 三条"看起来在守着，其实什么都没守"的坑

| 坑 | 形态 | 修法 |
|---|---|---|
| **恒真统计量** | 比较键里混进了不该有的字段 ⟹ 判据恒成立 ⟹ 报出 100%（例：推箱交换散度 342/342，因为比较键里含被推动的物体） | 进断言前先问「它**可能**不成立吗」；能构造一个让它是 0 的样本吗 |
| **没接线的仪表** | 断言"计数器在游玩时不增长"，但计数器从未被验证会增长 ⟹ 压根没接上也是绿的 | **先验仪表，再信读数**：先跑一次已知会触发它的路径，确认它会动 |
| **对照组选错** | 在"关卡全部来自缓存"的档位测"装载时会搜索" ⟹ 恒为 0，那条对比根本不成立 | 断言要选**该性质真的会发生**的样本 |

**通用判据（这条最值钱）：**

> 每条断言都问一句 —— **「如果被测的东西完全坏掉／或者压根没接线，这条断言会不会照样过？」**
> 会过 ⟹ 它不是断言，是**装饰**。

配套一条同样重要的：**统计量、比例、均值不进断言**（它们随样本池变化），进断言的是**整数**和**由设计意图推出的不等式**。

> **教训**：**一条判据测不出区别时，先怀疑判据的分辨力，再怀疑玩法。**
> 「两个玩法测出来一样」和「这个判据在这里失效」是两件事，前者会引你去砍掉一个好玩法。

## 3.3 变异测试：证明你的断言真的会失败

**能通过的断言不代表有效，能失败才算。** 对每种真实缺陷造一个变异体，跑一遍验证器，必须被抓到：

```js
const mutants = [
  ['判胜/判负对调',            (h) => h.replace(/a \? 'W' : 'L'/, "a ? 'L' : 'W'")],
  ['门控放宽 === 0 → < 2',    (h) => h.replace(/moveCount === 0;/, 'moveCount < 2;')],
  ['判据退回绝对下标奇偶',      (h) => h.replace(/return !info\.canWin;/, 'return i % 2 === 0;')],
];
```

**逃逸的变异有两种，必须分开对待：**

| 类型 | 判据 | 处理 |
|---|---|---|
| **等价变异**（行为保持） | 能论证二者在所有可达输入下等价 | 正常，无需补断言 —— 但要把**论证**写下来 |
| **真缺口** | 找得出一个输入序列能区分二者 | 立刻补断言 |

⚠️ **等价变异不仅要"把论证写下来"，更要让论证本身可执行。** 口头说"这俩应该等价"是自欺的高发区 —— 换成**跑一段独立脚本量化两者的差异**，差值为 0 或落在浮点噪声内才算等价：

```js
// 变异 A：权重整体等比缩放（0.7/1.6 → 0.35/0.8）—— 直觉上"改了配置"，实际等价
// 论证：归一化后累积概率完全相同。用独立脚本量出来，而不是嘴上说：
let maxd = 0;
for (let i = 0; i < ca.length; i++) maxd = Math.max(maxd, Math.abs(ca[i].c - cb[i].c));
console.log('最大累积概率差 =', maxd);        // 实测 0 ⟹ 等价成立

// 变异 B：越界回落分支改成常量 —— 直觉上"改坏了"，实际不可达
// 论证：累积概率上限 = 1.0000000000000002 ≥ 1，而 rand < 1 恒成立 ⟹ 回落分支永不进入
```

**这两类恰好相反**：A 是"配置变了但行为没变"，B 是"代码变了但那一行死着"。共同点是 —— **光看代码或光看断言结果都判不出来，必须量化**。

**等价变异必须存活**：如果它们被抓，说明断言在钉**实现细节**而不是**契约**，这种断言会在下次正常重构时误伤（把权重都减半的清理动作会被判成缺陷）。

**把"完整复原历史 bug 的组合变异"单独跑一次**（守卫 + 错误置位顺序），它必须被抓到 —— 这才是硬证据。本案例 6 个变异抓到 4 个，2 个逃逸经论证均属等价。

# 四、交付时要一起报的结论

**最优 AI 一旦落地，游戏就变成确定性谜题**：玩家一步走错就再也翻不回来。评估体验不能看"AI 强不强"，要看两个数：

```js
// 开局裁决 + 先手胜率 —— 精确算法：穷举全部盘面，按出盘概率加权
console.log('先手理论必胜率:', 0.8352);      // 本案例（基准均匀分布为 0.8583）
```

- 先手胜率高 → 玩家大部分局只要走对就能赢，任何失误立刻输 → 这是"找线"谜题，适合做学习/教学型原型
- 先手胜率接近 50% → 接近抛硬币，玩家会觉得 AI "赖皮"

**报数字时必须满足两条**：① 用**精确值**（穷举 + 概率加权），不要用模拟估计 —— 省事又不会有人质疑口径；② 表要带 **三列**（均匀基准 / 上一版 / 本次），否则看不出边际收益。该报哪几项、每项为什么重要（决策点分布比均值更该报，因为它掩盖手感变化），见 `references/design-criteria.md` 的「报数要带三列」。

**边际收益递减要主动说**：本例 20%→35% 用 −19% 的决策点只换来 +8.6pt 的必败率。如果用户还想加"转机"，更该动的是**其它维度**（本例：盘数 `n` 的分布）。

**该给用户摆的杠杆**（不要擅自加）：① 出盘分布调参；② 按概率的次优走法做难度梯度（代价是放弃可证最优）；③ 复盘/教练模式（终局公布开局裁决）；④ 让先手可控，避免开局就判死刑的局。

### ⚠️ 条件性 UI 就是答案播报器

凡是"看穿 / 识破 / 猜对"这一类**玩家声明式**机制，UI 绝不能提前透露裁决：

| 坏设计 | 后果 |
|---|---|
| 按钮只在必败局显示 | 按钮的存在 = 答案 |
| 按钮文案随裁决变色变字（"看穿败局" / "放弃胜利"） | 玩家不需要思考，读文案即可 |
| 按钮颜色随裁决变化 | 同理，颜色也是信息通道 |

做法：**按钮常驻 + 文案中性 + 结算才算账**。猜错的惩罚（判负）本身就是平衡器，不需要靠隐藏按钮。配套断言廉价且有力：**必胜局与必败局的按钮文案必须完全一致**（`textWin === textLose`），以及"必胜局按钮同样可见"。

### ⚠️ 给人看的产物，断言必须模拟"人怎么用它"

纸面原型 / 手动测试用的材料（图纸、卡片、速查表）同样是**代码产物**，但正确性只有人肉能验证 —— 这类 bug 不会让脚本报错，只会让测试得到假结论。

实战案例（关卡图纸导出）：内部逻辑坐标是 `(x, y)` 且带网格偏移，脚本把它原样印成「把 (3,2) 的箱子往 → 推」。但图纸是从 `(xmin−1, ymin−1)` 开始画的，**内部坐标 ≠ 纸上数出来的行列**，差一个偏移 → 主持者照着数只能数到一个空格，然后他会得出「玩家连这都推不对」的**假结论**。

修法两层，缺一不可：① **加行列标尺**（图纸上印 `123456789` 和行号）；② **加坐标断言守卫** —— 每一步印出的行列，在**当时那张图纸上**必须真画着箱子，最后箱子必须全在目标上。⚠️ 写守卫时自己又错了一次：拿**初始**图纸去对第 2 推 —— 被断言当场拦下。**守卫也要测。**

> **通用教训**：只要一个产物是给人读的，断言就必须模拟"人怎么用这个产物"，而不是"代码怎么生成这个产物"。否则脚本永远 100% 通过。

# 五、本机踩坑

- **`node` 里 `/tmp/x.js` 会被解析成 `D:\tmp\x.js`**（Windows 下相对当前盘符），报 `ENOENT`。临时文件用 `os.tmpdir()`。
  ⚠️ 更严的一条：**变异生成器/运行脚本这类"要被执行的文件"必须放在项目内**（如 `.mutbak/`），不能放临时目录 —— 某些环境下"写入侧工具"与"Bash 侧"看到的临时目录**不是同一个**，写入明明"成功"，Bash 却报 `No such file or directory`。放项目内可绕开这个歧义（用完删掉）。
- **沙箱里 `child_process.execFileSync` 起不来子进程**（`e.status === null`、stdout 为空），**别把这种空输出当成测试结论**。做法：用 node 只**生成**变异体目录，再用 bash 循环逐个 `node <dir>/verify-ai.mjs` 收退出码与 `✗` 行。
- **Windows 下源文件常是 CRLF，`replace` 的锚点用 `\n` 会命中不了"行尾含注释"的行。** `{ n: 6, weight: 1.6 },         // 注释\n` 这样的锚点在 CRLF 文件里是 `...注释\r\n`。改用正则 `[^\n]*\r?\n`，或先确认字节（`sed -n 'Np' f | cat -A`）再写锚点。
  ⚠️ **锚点没命中时必须让生成器报错退出**，否则"变异其实没生成"会被误读成"变异存活"。
- **项目若有"发布副本"（`site/index.html`）或其它一致性守卫，变异体必须连副本一起改。** 否则第一个失败的是副本一致性断言，你就分不清"是本次要验的那层抓到的"还是"被无关守卫挡下的"。生成器里对源文件的每个变异结果同时写进 `<dir>/index.html` 和 `<dir>/site/index.html`。
- Bash 工具启动时 PATH 被 shim 破坏，命令前需显式修复：`export PATH="/usr/bin:/bin:$HOME/.workbuddy/binaries/node/versions/<版本>:$PATH"`。
- 用 `node --check <抽出的脚本>` 做交付前语法校验（单文件 HTML 无法直接 `--check`）。
