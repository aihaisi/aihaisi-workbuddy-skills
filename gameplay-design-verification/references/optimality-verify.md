# 最优性验证的深挖：暴力参照、变异清单、规则展开

> 配套 `gameplay-design-verification/SKILL.md` 第 2、3 节。SKILL.md 只有流程与判据，实现细节在这里。

## 1. 暴力参照：博弈树 DP

```js
function bruteWin(a) {                     // 返回 win(当前盘下标, 该盘剩余)
  const memo = new Map();
  function win(i, m) {
    if (i >= a.length) return false;       // 无子可取 → 判负
    const key = i * 1e7 + m;
    if (memo.has(key)) return memo.get(key);
    let res = false;
    for (let take = 1; take <= m && !res; take++) {
      const next = take === m ? win(i + 1, i + 1 < a.length ? a[i + 1] : 0) : win(i, m - take);
      if (!next) res = true;
    }
    memo.set(key, res);
    return res;
  }
  return win;
}
```

状态数爆炸前先算清楚：n ≤ 5、a_i ≤ 4 就有 1364 个盘面 / 约 1.6 万个可达状态，够用。

## 2. 本案例的数字（可作为量级参考）

| 指标 | 旧 AI | 新 AI |
|---|---|---|
| 逐状态判对率（15930 个可达状态） | 50.8% | 100% |
| 进入"随机捣乱"分支时**实际是必胜态**的比例 | 73.5% | — |
| 先手对局胜率（vs 旧 AI） | 6.4% | 96.6% |

旧判据错在哪：用**绝对下标奇偶**（`firstGT1 % 2`）判胜负，而正确判据是**相对于盘尾的距离**。绝对下标一路错，且 m 不参与判断 —— 但 m ≥ 2 必胜是第一条定理，判据里不出现 m 本身就已经暴露了问题。

## 3. 出盘分布侧的变异清单（只差几个百分点，肉眼 review 发现不了）

第一、二轮共 13 个，**13/13 全被抓**：

| 变异 | 意图 |
|---|---|
| 概率退回上一版 / 抬过头 / 设成 0 | 数值被误改、或被"顺手清理" |
| **反解公式漏掉 `(1−p)` 归一化** | 最隐蔽的一个：35% 只偏到 25.93% |
| 其余档被压歪（不再等概率） | 提了一档却把别的档带歪 |
| 抽样器忽略权重倍率 | 配置改了但没接上线 |
| 档位上界写错 / 盘子数上界改小 | 值域被悄悄改窄 |

**带权分布（多档不同概率）的变异清单**（第三轮 7 个，**7/7 全抓**）：

| 变异 | 意图 |
|---|---|
| **删掉某个档**（n=3 被移除） | 值域被悄悄收窄 —— 断言须钉死**全部档位**的字面量，不能只钉上下界 |
| **把某档放大成主力**（权重 0.7 → 9.0） | 极端值反转（变体变成主流），需单独断言"该档占比 ∈ [10%,16%]" |
| 上限退回 / 上限悄悄提高 | 值域被改；提高的那侧同样要拦（新增档位更容易漏） |
| 权重表全改均匀 | "带权"这个设计意图被抹平 |
| 抽样器比较符反向（`<` → `>`） | 累积查表逻辑写反 —— **单调性断言**专抓这个 |
| 越界回落分支改常量 | 见"等价变异 B"（不可达 ⟹ 应存活） |

注意最后两行：一个该抓、一个该放。**`<` 反向**会让分布完全错乱（该抓），而**回落分支**死着（该放）。**同一次测试里必须同时包含"该抓"和"该放"两类**，否则你不知道自己的断言是精准还是过拟合。

## 4. 把 DP 展开成"人能用的规则"，当作交付物之一

闭式递推能跑通就够用了，但**把它展开成一条人类可读的规则**往往能直接解释"这个玩法的转机在哪"，价值大于再写十行注释。本案例：

```js
// lose[j] = (a[j] === 1) ? !lose[j+1] : false   展开后 ⇒
// 数"紧随其后的连续 1 蘑菇盘"长度 r：
//   a[j] >= 2                                → 必胜
//   a[j] === 1 且 1 链被 >=2 的盘截断        → 必败 ⟺ r 为奇数
//   a[j] === 1 且 1 链延伸到盘尾             → 必败 ⟺ r 为偶数（基准被"盘空判负"翻转）
```

⚠ **展开时最容易漏掉"链延伸到边界"这一支**：本案例第一版就漏了，随机 20 万盘面立刻报错。所以规则写完后必须**穷举小空间全量盘面**交叉验证（`n ≤ 6, a_i ∈ [1,6]` 共 55986 个），而不是抽几个例子看着对就收。

## 7. ① 结构性质那一层的完整推导（本案例）

顺序取蘑菇（n 个盘子串行解锁，每次从最左未空盘取 1~k 个，取最后一个的赢）：

> **当前盘剩余 m ≥ 2 ⇒ 轮到的人必胜。** 因为他要么一次取空把"开局必败的下一盘"丢给对手，要么只留 1 个把对手顶住，二者必居其一。

**推论：必败态必然是 m == 1，而 m == 1 时走法唯一。** 所以 ——

> 最优 AI **不存在** "必败时怎么挣扎"的自由度。任何 `if (必败态) 随机取` 的分支都是错的，
> 随机只会把本来赢的局输掉。**"必败时随机捣乱等玩家失误"是伪需求。**

想让它"给玩家机会"是**难度设计**问题，应该显式引入按概率的次优走法，而不是藏在必败分支里 —— 但那样会放弃"可证最优"这个性质，见 `design-criteria.md` 判据十末尾的三条路。

**这一步的价值**：一条定理直接省掉整段"必败态怎么走"的代码，而且把后续所有验证都简化成"查表 vs 暴力 DP 对账"。**先证结构性质，再写 AI。**

## 6. 跨实现对账：把「同量级」升级成「逐局同分」

**当同一个玩法有两个实现**（JS 原型 + Python 模拟，客户端 + 服务端，或"优化前 / 优化后"两版求解器），"两边数量级吻合"是一个几乎无用的断言 —— 差 10%、差一倍都能叫"吻合"，而差异可能来自物理不一致、也可能只是采样噪声，**分不清**。要做的是让两侧跑**同一批对局**：把随机源换成一个十几行的 LCG。

```js
// JS 侧复现 Python 的 x = (1103515245*x + 12345) & 0x7FFFFFFF
const lcgSeq = (seed, n) => {
  let x = seed >>> 0; const out = [];
  for (let i = 0; i < n; i++) {
    x = (Math.imul(1103515245, x) + 12345) & 0x7FFFFFFF;   // imul = 低 32 位，与 Python 全精度后取模等价
    out.push(SHAPES[x % SHAPES.length]);
  }
  return out;
};
```

**别用 `random.Random` / `mt19937`**：梅森旋转没法在 JS 里低成本逐位复现。对账脚本里"两边拿得到同一个数"比"随机性更漂亮"重要得多。序列长度、投放上限两侧必须**同步**，否则会在上限处出现假失败。

对账分三层，从强到弱，缺一层就会误判：

| 层 | 策略 | 能证明什么 |
|---|---|---|
| **A 物理** | 确定性「最左合法列」，× 所有朝向 | 坐标约定、下落起点、出生判定、消行补行位置一致 |
| **B 评估** | 同一序列跑贪心（带评估函数） | 评估口径、tie-break 方向、候选集过滤一致 |
| **C 分布** | 同一批 N 局 × 上限块数 | 端到端一致（含消行累积效应） |

**只做 C 会漏掉 A/B**：总分相同也可能是"错的地方互相抵消"。逐步 trace 比总分更早报警。trace 里除了位置还要打**朝向序号**（`name@col#orient`）—— 同一列配不同朝向是两个局面，不打朝向就没法归因。

**对账抓出来的四个坑，没有一个能靠"看代码"或"跑单局"发现：**

| # | 症状 | 根因 |
|---|---|---|
| ① | 首步读到 `J@0`，另一侧是 `I@0`，像物理不一致 | **注入确定性序列时没重置模块内部的游标**（`pieceIdx`）。初始化里已经生成过一块，只换序列＝整条错一位，对账出的"差异"全是假的 |
| ② | 24 个候选的评分表里只有 **1 格**不同 | **评估器漏算消行**：分数要在消行**后**的棋盘上取最高列。差一格就足以让贪心选错，60 块后总分拉开一倍 |
| ③ | 中心堆满、两侧空着也判负 | **出生判定只查中心列**：宽 4 的块要占 4 列，等于把死亡判定放大 4 倍。玩家读到的是"游戏乱判"。败因必须由棋盘状态决定 |
| ④ | `ReferenceError: Cannot access 'X' before initialization` | 常量声明在调用点之后（TDZ）。测试文件是**顺序执行**的，公共 helper 必须定义在第一次使用之前 |

**方法论（这条比上面任何一条都重要）：**

> **分数差一倍时，第一反应必须是"先证明我们在玩同一个游戏"，而不是怀疑机制。**
> 否则你会去改机制 —— 把正确的东西改坏。

配套做法：给评估器加一个 `DBG=1` 环境变量，打印**候选评分表 + 棋盘快照**。两条实现各打一张，逐行 diff。只看"最终选了哪个"，永远分不清"候选集不同"和"同一落法评分不同"。
