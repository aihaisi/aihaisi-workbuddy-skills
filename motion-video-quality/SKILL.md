# 动效视频的质量量化与修法

## 0. 按症状分诊

**核心原则：别用直觉回答"够不够活""看不看得懂"，换成可计数的量，并且拿对标作品定标尺。**

| 症状 | 量什么 | 判据 | 修法 |
|---|---|---|---|
| "像 PPT" | 动效密度画像 + 运动分布热力图 | 见 §2 验收线 | 放覆盖全屏的高频结构层；让主体更大 |
| "这一段卡住了" | hold 段内容区净运动 | < 0.05 即冻结 | 让**内容本身**持续动（别只加淡光带） |
| "节奏太赶/太拖" | 章节时长 + 字幕条数 | 见 §5 | 调时间轴三段式比例 |
| "看完还不理解" | 屏上文字术语密度 + 算式长度 | 见 §4 | 术语清零，算式换成人/物的数量对照 |
| "封面缩到手机糊了" | 按真实显示尺寸缩出来看 | 见 §6 | 差别必须是**形状/位置/数量**的差别 |
| "不知道起什么标题" | 对标作品标题句式 | 见 §7 | 疑问句 + 日常困惑 |

## 1. 三个仪器

`scripts/` 下三个脚本，零项目依赖（只要 ffmpeg + numpy + PIL，掩码模式另需 scipy）。

```bash
PY=python                        # 需 numpy / PIL / scipy
S=<skill>/scripts

# ① 动效密度画像：全片标量 —— 必须先跑，它决定"要不要动大手术"
python $S/motion_profile.py 成片A.mp4 对标作品.mp4     # ★ 必须并排跑

# ② 运动分布热力图：运动发生在画面的哪个位置
python $S/motion_map.py 成片.mp4 map.png 标签

# ③ hold 段冻结检测：只在内容像素上量
python $S/check_motion.py 成片.mp4 "390,870,1260" --bg-dir <纯背景帧目录>
```

**§1.1 纯背景帧目录怎么来。** `check_motion.py` 要一批**与成片同帧号**的纯背景图，命名 `f%05d.png`。
前提是背景被设计成**全局帧号的确定性函数**（如 canvas 里 `drawBackground(ctx, W, H, f)`）——
这样同一帧号能精确复现。本项目用 `library/tools/render-bg.js` + `src/bgonly.html` 生成。

⚠️ **背景帧必须传全局帧号**；传章内帧号会让每章开头跳回去，参考帧全错。

## 2. "像 PPT"的定量定案

### 2.1 物理事实（这条决定了所有修法）

> **平色区域无论怎么平移、缩放，逐帧差异都是 0。**

所以"让元素动起来""加个镜头推拉"**救不了**大片平色背景。
热力图上的黑区不是"动得慢"，是"这里没有能被察觉的高频结构"。

### 2.2 验收线（对标同风格赛道实测）

| 指标 | 合格线 | 说明 |
|---|---|---|
| 均值 | **≥ 2.0** | 常年有多大的变化 |
| p90 | **≥ 4.0** | 高峰有多高 |
| p10 | **≥ 0.13** | 地板不能太死 |
| 近静止比（MAD < 0.20 的帧占比） | **≤ 13%** | 有多少时间是死屏 |
| 变化 > 0.2 的像素占比 | **100%** | 有没有"从来没变过的区域" |

对标读数（可直接当参照系）：某 56 万赞作品 **2.721 / 4.24 / 0.245 / 5.9% / 100%**。

**只跑 `motion_profile.py` 会漏掉最关键的诊断。** 一定要配 `motion_map.py` 看热力图：
亮区只堆在画面中间、四角大片纯黑 = 约 30% 的画面从来没变过 ⇒ 这才是"像 PPT"的真身。

### 2.3 修法（按性价比排序）

1. **放一层覆盖全屏、有高频结构的层**（星野视差、颗粒滚动、细网格…）。
   这是唯一能救"四周纯黑"的办法 —— 平色区靠元素平移永远救不回来。
2. **让主体更大。** 实测内容往往只占画面 5%–21%，p90 上不去是因为主体太小。
3. **平面色块 → 立体物体。** 两个色渐变的圆角矩形 vs 有正面/侧面/顶面 + 横向高光 + 底部反光的立体块，
   是"新手感"和"专业感"的分界，且一次改造全片受益。
4. **入场方式决定"活不活"。** 淡入 = PPT；**生长 / 落下 / 被描绘出来** = 动画。
   同一个元素，改成"被画出来"就够。

🔴 **颗粒只抬地板、不造高峰。** 实测把 p10 从 0.009 抬到 0.635（甚至超过对标上限 0.245），
但 p90 几乎不动 —— 它把动态范围压平了。**p90 低的问题不能靠加颗粒解决。**

## 3. hold 段冻结检测（最容易被漏的一类缺陷）

### 3.1 判据

| | 值 | 来源 |
|---|---|---|
| 有意义运动的下限 | **0.05** | 源帧平移 1px ⇒ MAD ≈ 0.8367；H.264 压缩噪声 ⇒ ≈ 0.005 |
| 检查窗口 | 每章末尾连续 **5 帧** | 拿一章的最后一帧往前取 5 帧 |

### 3.2 有全屏动态背景时，必须在「内容区」上量

**两种错法，都别用：**

| 错法 | 症状 |
|---|---|
| 看全帧 | 背景颗粒自身帧间 MAD ≈ 2.15，把读数抬到 1.4–2.1 ⇒ **内容真冻结也"通过"** |
| 扣背景基线 | 背景参考帧全帧都是颗粒，成片里大片被不透明内容盖住 ⇒ 相减**全是负数**。负残差说明的不是"没动"，是**减错了** |

**对法**：
```
内容掩码 = |成片帧 − 纯背景帧| > 16 灰阶        # 内容明显亮于背景
掩码     = 向内腐蚀 4 像素                      # ★ 关键
净运动   = 掩码内相邻帧差的均值                  # 阈值 0.05
```

🔴 **腐蚀这一步不能省。** 掩码的**边界环**是「半覆盖」的抗锯齿像素 ——
那里背景颗粒露在外面照样在动，会被算成"内容运动"。
实测（内容完全静止的合成样本，背景在滚）：

| | 净运动 | 判定 |
|---|---|---|
| 未腐蚀的掩码 | 0.0776 | 误判为**通过** |
| 腐蚀 4px 后 | **0.0012** | 正确判出**冻结**（内容内部仅 0.0001） |

边界环只占掩码的 ~10%，却贡献了读数的 ~98%。

### 3.3 🔴 「内容区」量的是内容，不是"整屏有没有变化"

**已知边界（报结论时必须一起说）**：
掩码只覆盖**不透明、比背景亮**的像素。所以它答的是
**"内容有没有动"**，不是"屏幕上有没有任何变化"。

因此：一条**又宽又慢**的柔光带（如 620px 宽、每帧移 22px、alpha 0.085）
在任一像素上每帧只变化约 1–2 灰阶 —— **它救不了这个判据，也确实救不了观感**。
⇒ **修 hold 冻结要动内容本身**（光标闪、数值跳、某行重打、元素呼吸），
不要指望加一层淡光带就能"续命"。

### 3.4 一次要取很多帧时，别逐帧调 ffmpeg

对每个帧号单独跑一次 `ffmpeg -vf select=eq(n,f)` 会**每次都从头解码**——
几十个检查点会慢到分钟级、甚至被外层超时杀掉。改成一次解码 + `select` 多帧：

```bash
ffmpeg -i in.mp4 -vf "select=eq(n\,385)+eq(n\,386)+eq(n\,387)" -vsync 0 f%05d.png
```
⚠️ `-vsync 0` 输出的编号是**顺序号**，不是原始帧号 —— 第 k 个文件对应排序后帧号列表的第 k 项。
数量对不上就必须降级重取，否则帧号会整体错位（错位后读数看起来仍"合理"，极难发现）。

**改动任何检测逻辑后，必须重跑一次已知样本**（见 §8.2），否则无法排除"仪器的锅"。

## 4. 「观众看不看得懂」也是可量化的

别只靠感觉。扫全片屏上文字，统计两项：

| 量 | 阈值 | 超了怎么办 |
|---|---|---|
| 学术术语出现处数 | **0** | 全换成日常词（"加权平均"→"关键在人数"） |
| 单个画面上算式项数 | **≤ 3** | 把 Σ 算式换成人/物的数量对照（"男生 560 人 vs 女生只有 25 人"） |

真实案例：某版被反馈"不易理解"，扫出 **5 处术语 + 12 个乘法项** ——
**问题是表达方式，不是内容不够**（那一版的机制其实讲得比前一版还全）。
同一条片改完之后，术语 0 处、算法只剩人数对照，反馈即转正。

**判断"要不要加内容"之前，先扫一遍术语密度和算式长度。**

## 5. 节奏契约

| 项 | 规格 | 为什么 |
|---|---|---|
| 时间轴三段式 | 起手 0–15% / 展开 15–70% / hold 70–100% | 起手要快，hold 不能长 |
| 单章时长 | 13–20s（章节级资产 390–600 帧 @30fps） | 对标作品实测 |
| 成片总长 | **100–170s** | 对标 10 条实测，**无一低于 60s** |
| 字幕 | `cues[]`，**2–3s 一句**；淡入 **8 帧** | 单条字幕撑不起一章；16 帧淡入 = 每 2.5s 有 0.5s 发虚 |
| 音效 | 三档：`tick`（转场）/ `ding`（揭晓）/ `hit`（重音，全片 2–3 次） | **每一次"视觉揭晓"配一声"叮"** —— 对标作品 8/8 命中 |
| 音效"清脆" | 靠 **2ms 起音 + 少分音 + 快衰减** | **不是靠提高频率** |
| 音频电平 | 用**绝对电平**控制，RMS −9~−11 dBFS | 不做"峰值归一化后再提 RMS"（内容稀疏时算歪）；**不做饱和**（低频饱和产生嗡声） |

🔴 **hold ≠ 冻结。** 校验器要拦"非片尾 hold"。
🔴 **`duration` 必须 == 资产的 `frames`**，否则超出部分钳到最后一帧 = **尾段整帧冻结**（踩过 2 次，肉眼极难发现）。

## 6. 一切按「手机尺度」设计

1920 宽的帧在手机上约 **540px**（28%）。封面 1080×1440 缩到信息流约 **270px**。

🔴 **要在小尺寸下传达的差别，必须是形状 / 位置 / 数量的差别** ——
不能是描边粗细、透明度、辉光。

> 实例：封面要用"12 个方块 + 虚线框"表达"这里有连着同色的簇"。全尺寸看着没问题，
> 缩到 270px **直接糊掉**（试过加粗虚线、加金色柔光底衬，都不够）。
> 改成**把连续同色合并成一条长块**（内部留细缝保住可数性）后，
> 上条呈"大小不一、黏在一起的块"、下条呈"12 个均匀格子"——形状本身的差别在任何尺寸都成立。

🔴 **验证方式：按真实显示尺寸缩出来盯着看**（封面 270px / 帧约 540px），**不要只看全尺寸**。
另外，"画得碎"不如"画得少而大"：小图标一类元素，一行放 6 个会挤到手机认不出的尺寸。

## 7. 发布：标题 / 标签 / 落点

**标签只占三成，七成在文案落点。**

### 7.1 标题

爆款标题的形态高度一致：**疑问句 + 指向一个日常困惑**（不是指向知识点）。

```
最"笨"的程序，为什么赢了所有老狐狸？
老实人凭什么总吃亏？
谁先开口，谁更如愿？
```

两条硬约束：
- 🔴 **标题不能是答案。** 把片中落点句直接当标题 = 开场剧透，划掉。
- 🔴 **标题要和封面互补，不能重复。** 封面已经占了"反直觉"这个位置，标题就去占"日常现象"。

### 7.2 标签（三层，**总共 4–6 个**）

```
第 1 层 身份（必带）  #vibe知识大赏  #claude5.5
第 2 层 垂直（2–3）   #概率 #随机 #统计学 #博弈论 #辛普森悖论 …
第 3 层 泛流量（1–2） #底层逻辑
```

- 拆过的真实作品中**没有一条超过 6 个标签** —— 这个体裁靠话题池精准，不靠数量。
- desc 固定前缀：`Vibe知识大赏 ｜ 《片名》` + 一句疑问句标题。
- ⚠️ **别混**知识向的 `#vibe知识大赏` 和互动内容向的 `#VibeCoding大赏`。
- ⚠️ **`#认知觉醒` 慎打** —— 它是"励志/鸡汤"池的强信号。

### 7.3 🔴 落点决定进哪个池（比标签本身重要）

平台的 `video_tag` 是**自动归类**，由文案**最后两句**决定。同样的体裁和制作方式，落点不同进完全不同的池：

| 落点 | 进哪个池 |
|---|---|
| 停在**现象 / 机制 / 方法** | `科普 · 数理科学`（对标 56 万赞所在的位置）✅ |
| 落到"所以你该怎么做 / 你要长个心眼" | `励志 · 鸡汤` ❌ |

⇒ **desc 最后一句必须落回事实，不要落向劝诫。**

### 7.4 取证与核验（做这类选题时的纪律）

- **判生成式 vs 代码渲染**：400% 放大看文字图表 —— **文字锐利 + 数值精确到个位 = 生成式做不到**（最快排除判据）。别用低阈值在暗背景数"亮点"，那是压缩噪声。
- **屏幕上出现的每个数字都要有出处**，并在物料里留一张事实核验表（数字 → 论文/发布会/官方博客）。
- 🔴 **"总体率 + 分层率"同时出现时，口径必须写在画面上**，且各自的**分母要标清** —— 混用 = 事实错误，观众也必然要问。

## 8. 两条纪律（比上面任何一条判据都值钱）

### 8.1 一条判据测不出区别时，先怀疑判据的分辨力，再怀疑产品

「两个东西测出来一样」和「这个判据在这里失效」是两件事。
后者会让你砍掉本来正确的做法。

**通用问句：如果被测的东西完全坏掉，这条断言/判据会不会照样通过？**
会 ⇒ 它不是判据，是装饰。

### 8.2 先证明检测器有效，再相信它的"无异常"

新写的检测器**必须拿已知样本校准**，两个方向都要：

```bash
# ① 造一个"已知冻结"的样本：内容固定不动，只让背景动
python - <<'PY'
import numpy as np, os
from PIL import Image
for i, f in enumerate(range(BG0, BG0+5)):      # 用纯背景帧当底
    a = np.asarray(Image.open(f'bg/f{f:05d}.png').convert('RGB')).copy()
    a[400:700, 700:1200] = (240, 240, 240)     # 静态内容块：逐帧位置完全相同
    Image.fromarray(a).save(f'frz/f{i:05d}.png')
PY
ffmpeg -y -framerate 30 -i frz/f%05d.png -c:v libx264 -pix_fmt yuv420p -crf 18 frozen.mp4

# ② 它必须被判 ❌（抓不到 = 检测器坏了）
python $S/check_motion.py frozen.mp4 "5" --bg-dir bg
```
⚠️ **合成样本的帧号必须与背景参考帧号对齐**（上面 `f{i:05d}` vs `f{f:05d}` 要对得上），
否则检测器会正确降级成"看全帧"，你会把"降级"误读成"失效"。
⚠️ 反向也要做：拿一段**已知在动**的片段跑，它必须通过。

**又一条同族纪律：仪器报异常时，先量"被测对象的绝对量级"，再怀疑它缺失。**
实例：音效检测器漏掉 7 个重音，第一反应是"音效没放"。实测该档音效绝对能量
**0.319 是三档里最高的**（另两档 0.112 / 0.241）⇒ 产品没问题，是仪器错
（0.85s 的长音能量包络太宽，`medfilt` 基线被它自己抬高）。改用**能量上升沿**检测即修复。
**一个数字就能定案，不必靠推理。**

### 8.3 本机环境坑（Windows）

- 临时文件路径：Python 看到的 `/tmp` 与 Git-Bash 的 `/tmp` **不是同一个目录**。
  跨工具传递路径时**一律用 Windows 绝对路径**（`C:/Users/.../AppData/Local/Temp/...`）。
- Bash 工具启动时 PATH 可能被 shim 破坏，命令前显式修复：
  `export PATH="/usr/bin:/bin:$PATH"`。
- 长耗时命令会被前台超时 SIGTERM；被 SIGTERM 后**管道里的输出会丢**。
  写成 `> log.txt 2>&1` 再读文件，或放后台跑。

## 9. 出片前的验收清单

| # | 检查 | 工具 / 判据 |
|---|---|---|
| 1 | 帧数与时长一致 | `duration == frames/fps`，精确到小数 |
| 2 | 每章 `duration` 恰等于资产 `frames` | 不一致 ⇒ 尾段整帧冻结 |
| 3 | 动效密度达标 | §2.2 五项，与对标并排比 |
| 4 | 热力图无"从来没变过的大片黑区" | `motion_map.py` |
| 5 | 每章 hold 段内容在动 | `check_motion.py`，全部 OK |
| 6 | 术语密度 0、算式 ≤ 3 项 | §4 |
| 7 | 封面按 270px 缩出来看得懂 | §6 |
| 8 | 音效落点全命中 | 分带（每档只用自己基频附近的窄带）+ 能量上升沿 |
| 9 | 抽帧目视：首帧 / 中段 / 末帧 | 不是黑帧、不是字体回退 |
| 10 | 重复渲染一致性 | 渲染两次比像素差 —— 这是"确定性"的唯一硬证据 |

⚠️ **别把机器渲染时间算成人力工时。** 按默认加速配置（jpeg q100 + 6 进程，见
`code-rendered-video`）是 **25 帧/秒**量级，4500 帧 ≈ 3 分钟；保守配置（png 单进程）
是 3 帧/秒量级、≈ 22 分钟。两种都是机器在跑。

🔴 **换了渲染参数（中间帧格式 / 进程数 / GPU 开关）之后，这份清单必须整份重跑一遍。**
实测教训：把中间帧从 PNG 换成 JPEG 提速 5 倍后，画面上看不出任何差别，但成片元数据
悄悄变成了 `yuvj420p` / `color_range=pc`（JPEG 是全范围，ffmpeg 原样继承）——
**同一工程两套规格、不同播放器解出的亮度不同**。是帧数断言的报错把人引过去的。
⇒ 提性能的改动一律当作"可能影响成片"来对待，别只比肉眼。
